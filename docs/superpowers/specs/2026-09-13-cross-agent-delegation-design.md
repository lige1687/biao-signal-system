# Codex 向 CC / ZCode 派工：最小受控方案

日期：2026-09-13

## 1. 目标

让当前 Codex 对话可以把一个边界明确的研发任务交给 Claude Code（CC）或
ZCode，执行期间由不调用模型的终端看板展示状态，收到结构化结果后由 Codex
复核，再由用户决定是否继续。

这属于研发任务编排层。它不进入 `web/`，不接交易运行时，不修改交易判定、
规则账本、行情数据或交易计划。

## 2. 已核实的本机条件

- Codex CLI：`codex-cli 0.153.4`。
- Claude Code：`2.1.258`，支持非交互输出、结构化结果、后台任务与恢复会话。
- ZCode 桌面版：`3.8.1`，内置 CLI `0.16.3`：
  `/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs`。
- ZCode CLI 支持单次提示、JSON 输出、只读计划模式、最大轮数与恢复会话。
- 当前仓库有大量未提交改动，因此首次联调只允许只读任务。

## 3. 方案比较

### 方案 A：统一 CLI 委派器（采用）

由一个本地脚本把同一张任务单翻译成 CC 或 ZCode 的命令参数。`start` 快速返回
任务编号；后台 runner 把执行端当作前台子进程管理并记录结果，模型不参与轮询。

优点：依赖少、权限清楚、容易停止、能单独验证两个执行端。缺点：不同 CLI 的
返回格式需要做一次归一化。

### 方案 B：MCP 桥接

把两个执行端包装成 MCP 工具。自然语言体验更完整，但第一版需要额外的服务、
配置和生命周期管理，暂不采用。

### 方案 C：桌面界面自动控制

由 Codex 打开 ZCode 输入任务。它可以作为 ZCode CLI 失效时的备用通路，但界面
变化容易使流程失效，不作为默认实现。

## 4. 第一版组成

### 4.1 统一委派脚本

新增项目级开发脚本，提供以下输入：

- 执行端：`cc` 或 `zcode`；
- 工作目录；
- 任务正文；
- 模式：`review` 或 `edit`；
- 最大执行轮数或超时；
- 允许读取、允许修改的文件范围与预先批准的验收命令；
- 幂等请求编号，避免主控没有收到返回时重复启动同一任务。

脚本提供 `doctor`、`start --dry-run`、`start`、`list`、`status`、`logs`、
`result`、`stop` 和 `dashboard`。`start` 只负责校验、登记、启动 runner 并返回任务
编号；runner 捕获标准输出和错误、执行超时和停止、核对实际文件变化、运行预先
批准的验收命令并生成交接摘要。

运行记录写入 `~/.local/state/agent-delegate/`，不污染仓库，也不保存 API 密钥。
默认落盘的是先脱敏再写入的事件和日志，不承诺保存含敏感信息的原始输出。

### 4.2 隔离工作副本与实际范围约束

执行端不直接进入来源工作区。runner 根据 `--read-path` 把明确授权的材料复制进
任务独占目录，`--write-path` 必须属于已复制范围；编辑任务只在该副本内修改，
第一版不自动回写来源工作区。

runner 在启动前记录副本基线，结束后自行统计新增、修改和删除文件。超出
`--write-path` 的变化一律判为范围违规，不能进入成功状态。执行端自述的改动只作
说明，不能代替 runner 观察到的实际变化。

### 4.3 统一任务单

每次派工都包含：

1. 目标；
2. 允许读取和修改的范围；
3. 禁止事项；
4. 验收标准；
5. 必须返回的内容：结论、改动文件、验证结果、未解决问题。

任务正文明确要求执行端不得继续派生其他 Agent，不得自动开启第二轮。

### 4.4 无模型终端看板

runner 把结构化事件增量写入 `events.jsonl`，把当前状态原子写入 `state.json`。
终端看板每秒读取这些小文件，显示任务编号、执行端、阶段、已用时间、最近一次
真实输出时间、最近已知活动及验收状态。

runner 心跳与执行端进展分开显示；没有事件时只显示“输出静默”，不伪造完成
百分比。看板关闭不停止任务，看板刷新不调用 Codex、CC 或 ZCode。

### 4.5 Codex 调用说明

新增项目级 Skill，让用户可以说“把这个交给 CC”或“让 ZCode 复核”。Skill 只负责
选择执行端、生成任务单、调用统一脚本并复核结果，不自行放宽权限。

## 5. 权限和停止规则

- 默认 `review`：CC 使用 `--restricted`、计划模式和明确的只读工具集合；ZCode
  使用 `--mode plan`，但在本机验证其权限和输出契约前只允许进入临时测试副本。
- CC 禁用 Bash、写文件、MCP、Hooks、Slash commands 与子 Agent；验收命令由
  runner 另行执行，执行端无权从回答中追加命令。
- `edit` 必须显式给出允许修改的文件范围；同一来源工作区同一时间只允许一个
  任务占用。第一版只产出副本内改动和补丁，不自动应用。
- 第一版每次只调用一个执行端一次。结果有问题时停下来，由用户决定是否重跑。
- 超时、非零退出、输出无法解析、执行范围扩大时，状态记为失败，不自动重试。
- 不使用绕过审批或取消沙箱的危险参数。
- 当前脏工作区的首次联调只能读取，不允许修改。

runner 使用参数数组启动执行端，不拼接 shell 命令字符串。执行端拥有独立进程组；
停止或超时时先发送 `SIGTERM`，宽限期后仍存活才发送 `SIGKILL`，并记录清理结果为
`confirmed`、`incomplete` 或 `unknown`。不得使用可能误伤其他会话的
`pkill -f claude`。

## 6. 数据流

```text
用户任务
  → Codex 生成受控任务单
  → start 校验并快速返回任务编号
  → runner 在隔离副本调用 CC 或 ZCode CLI
  → 普通进程采集事件、管理停止、核对变更并保存脱敏结果
  → 终端看板读取状态文件，不调用模型
  → Codex 默认读取 handoff.md，必要时检查补丁、代码和测试证据
  → 用户决定结束、修改任务或再派一轮
```

## 7. 状态与成功条件

状态限定为：`queued`、`running`、`completed`、`failed`、`stopped`、
`timed_out`、`interrupted`。第一版不实现在线等待审批；需要额外权限时以
`failed / permission_required` 结束。

`completed` 必须同时满足：执行端退出码为零、结果可解析且非空、没有范围违规、
任务单要求的验收全部通过、进程清理已确认、结果文件已经落盘。

`completed` 只表示执行端完成交付；同时写 `review_status: pending`，不代表 Codex
已经验收，更不代表允许合并。

每个任务目录至少包含：`request.json`、`task.md`、`state.json`、
`events.jsonl`、脱敏后的 `stdout.log` / `stderr.log`、`baseline.json`、
`changes.patch`、`verification.json`、`result.json` 和 `handoff.md`。

## 8. 验收

1. 先用假执行端模拟正常输出、空结果、非零退出、大量 stderr、半行 JSON、忽略
   `SIGTERM`、runner 中断、重复请求和范围违规，全部不调用模型。
2. `doctor` 与 `--dry-run` 不调用模型，能显示脱敏后的有效配置和能力缺口。
3. 关闭启动终端与看板后 runner 仍存活；超时和 `stop` 能停止任务进程组并记录
   清理结果。
4. 非法执行端、缺失任务、无效工作目录、目录穿越及符号链接越界在调用模型前失败。
5. 使用临时测试仓库分别向 CC、ZCode 派一个只读任务，两端均返回可解析结果，
   且来源仓库无变化。
6. 结果记录包含任务编号、执行端、状态、退出码、开始/结束时间、实际变化、验收
   证据、最终回答和待复核状态。
7. 不调用模型轮询；看板不展示没有事实依据的完成百分比。
8. 不修改 `web/`、`src/lei_signal/ui/`、交易规则或生产数据库。

## 9. 暂不做

- CC 与 ZCode 互相聊天；
- 多任务队列、服务发现、常驻服务；
- 网页管理界面；
- 自动恢复、自动重试、自动合并代码、自动提交或自动继续多轮；
- 在线审批、等待队列、优先级、自动选模型和模型互评；
- 常驻 HTTP 服务、WebSocket、消息总线与 LaunchAgent；
- 操控已有 ZCode 桌面会话；第一版为独立 CLI 任务。
