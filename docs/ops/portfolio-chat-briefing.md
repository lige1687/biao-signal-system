## 自然语言通用流程

用户可以说“我想买/已经买了/卖了/继续拿着，因为……；看至……；跌破……原理由就不成立”。先判断意图，不把讨论、假设或朋友交易写入用户事实。

### 准备交易或补原计划

从原话整理产品、交易理由、入场条件、目标、失效条件、止盈止损、盘中/收盘确认方式与持有周期，保留原话和当时日期。关键缺项一次只问一个，优先产品身份或失效标准。不能因为研究报告有数字就代用户填写原计划。

用户补充的原持有理由先保存在本机data/cache/portfolio-chat-briefing/user-context.json，随资料包读取；仅作为聊天待整理材料，不是生产计划或交易账本。不把个人原话自动变成技术条件。定投、估值买入等历史理由，先核资料与用户预期；没有退出条件就标未知，不要求用户事后编一个“当初止损”，不按趋势买入规则倒填历史。具体私人成本、原话和账户数据不写进版本化文档。

只先给确认卡，指出预计盈亏比的依据和不能算的部分；确认后复用系统计划创建/确认接口。系统已有holding-watch草稿与确认流程，但当前只按自身行情symbol识别，基金与指数错配时不能强行写入。确需扩展判定方式属于具体实施范围，先说明差额，不改权威策略含义。事后补计划标补录，不装成买入前已存在。

### 已发生交易

提取产品/份额类别、买卖方向、金额或确认份额、交易申请日、实际成交日/净值、费用（如有）、关联计划。给用户复核后，再走现有成交预览/确认；使用稳定请求身份防止重试重复记账。用户明确指令已包含全部事实且无歧义时不反复问同一信息，但仍按系统已有确认卡的落库流程执行。

申请、成交确认、持仓更新是三个状态。场外基金未确认净值/份额时只记录待确认事项；金额不能直接等同份额。记录后读取台账核对，不能只说请求成功。现有系统的priced只表示按交易日或更早净值做了记账定价，不能当成交易平台已确认的实际成交份额或价格。

现有fund_trades不会自动改portfolio_holdings这份旧快照。后续实际更新持仓前必须核对旧快照对应时点、交易是否已包含、份额/成本和重复身份；只在能对账时更新，核不清就保留待对账，不能按“旧市值加买入金额”伪造现值。当前未改任何真实持仓或成交库，自动对账接入尚未实现。

本次已将成交台账接入简报：trade_ledger.changes列相对上次读取的新增成交与定价等字段变化，pending_pricing列待定价记录，第一轮不冒充新增成交。报告须把这些变化及对账缺口列入对应产品；不要把台账自己计算的positions直接当成含29只旧持仓的完整账户。用户新报交易后，即便旧快照未更新，变化也应先在简报里看见。

## 产物与运行边界

- packet是本次只读资料快照，不取代持仓库、计划库或研究登记。
- 首次运行只建立比较起点，不声称“今日无变化”；重复刷新时间不算信息改变。
- 当前29只没有原计划与同产品技术结果，首次下午简报必须直接说明无法核对个人止盈止损。用户导入计划后才逐笔接入。
- 任何来源中断、截图失败、模型不能用、服务离线均保留实际失败；不重复重启、不扩大权限，不从旧报告补“最新”。
