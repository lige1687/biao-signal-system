## 关键变化如何运行

1. 读取本流程和portfolio-chat-briefing.md；先检查最近一次通知运行是否失败。此前若准备了事件文件却未在本聊天形成最终消息，先恢复那份报告并核当前事实，不因观察状态已推进就忽略未交付事项。状态文件不是送达回执。
2. 在仓库运行`PYTHONPATH=src python3 -m lei_signal.portfolio.briefing --slot 1440 --output-dir data/cache/portfolio-chat-briefing`。这次不额外抓取B站，复用已有两次日报的新抓取回执，避免重复请求；明确来源实际核查时间。即使取数退出2，也读取它已写出的数据包，把来源不可用列入检查。
3. 将返回的packet绝对路径传入`PYTHONPATH=src python3 -m lei_signal.portfolio.notifications --packet <路径> --state-dir data/cache/portfolio-chat-briefing/notifications`。默认只预览变化，不推进比较状态。
4. 读取返回report；核对里面的新变化及原数据日期，不仅看计数。再用相同packet加`--record-observation`保存已经检查的事实，读回结果。程序先存事件文件再原子更新比较状态；保留历史事件以恢复失败运行。记录观察不代表通知已送达。
5. 无事件安静。有事件时，与本聊天最近实际发出的11:35/14:40消息核对；刚讲过的同一事实不再完整重发。合并同一故障、同一产品，通常最多3条。内容包括发生了什么、影响什么、依据/日期、需要核对或处理什么。必要截图只围绕当前新事实，不每次重抓所有页面。

报告用语：接口不可用就说“暂时无法核对”，恢复就说“接口恢复可读取”；不自动说价格或基本面已实时。资料日期落后可能是休市或正常发布滞后，未核交易日历/预期发布时间时不得判断停止更新。当前程序仅比较来源自身明确的quality_status，不能自行加经济阈值。

计划变化只接受资料包已经认定可核的entered计划，保留data_as_of、actionable_from和研究代理限制。仍处盘中、缺行情或缺原计划时不判断已恢复，不重置原来可核的提醒。相同提醒持续存在、只有数据日期或抓取时间变化时不重复通知。实际条件变化或提醒解除须使用当前合格资料，并说明只是系统本轮状态，不等于可以买入。

成交只说台账新增/记录变化/定价状态变化。priced不等于平台已确认，原快照是否更新另核；离线或空响应不能解释成卖光。用户未明确报成交时不写真实账本。

第一次建立比较起点不会把29只原有资料缺口当作29个新报警；这些限制已经在原简报流程说明。比较状态、消息准备与送达分别陈述。代码只读来源并写本仓通知缓存，不改生产策略、计划、持仓、新闻或研究登记。

## 一周复盘如何运行

时间窗口为本次北京时间向前7天；先写实际截止时间。读取本周已保存简报、通知事件和本聊天实际报告，不能凭新抓取时间把旧资料归为新成果。更新当前持仓/成交读取；未导入的历史交易和旧市值不能用于计算真实账户周收益。

研究部分读取最新coordination/lei的原负责人记录、docs/experiments/registry.json及本周相关报告/回执。按修改内容判断，不按文件更新时间判断“新研究”。不扫描所有旧raw，不重新跑实验，不向其他聊天发消息。首次没有周对照时说明建立起点；负责人completed/论文摘要/测试通过都不能单独当成策略有效。

只整理三组信息：

- 持仓与执行：用户确实确认的新成交、原计划变化、明确无法核对项；没有完整账户来源就不报胜率或账户周收益。
- 本周真正交付：至多3项。每项一句“原来有什么问题、现在多了什么可用东西/得到了什么结论、证据在哪里、对日常交易有什么用”，区分功能、资料资格、历史研究和真实使用。
- 下周需关注：至多3项有明确理由与负责方的事项。已有负责人工作的只列状态；只有确需用户资料/决定才问，不把可自行查证的问题交还用户。

保留负结果和“没有增量”。若一周都是工程进展，直接说本周尚无新增可用交易依据。引用收益/成功比例必须核对象、时期、样本、成本和研究范围；不把有限历史结果外推到当前29只持仓。

周复盘的安全摘要和引用保存在本机data/cache/portfolio-chat-briefing/weekly下，供下周比较，包含私人内容的材料不进Git。周报只读汇总，不接管研究owner或做新实验，不写OKR。出现独立重要失败或需用户决定的阻塞时可通知；同一周已解释且未变化的旧卡点不重复堆砌。
