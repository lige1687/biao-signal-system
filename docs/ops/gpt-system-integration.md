# LeiSignal 接入 Codex

负责人为当前讨论对话，协调任务daily-trading-system-audit。日常查询、计划整理、成交记账和持仓对账使用原系统。用户最新取消主动推送，改为在自己询问或点选时回答；四个原提醒任务均暂停，旧独立提醒对话保留历史。本改造服务执行、复盘和消息解释，不改变策略或阈值。

## 按需查看菜单（2026-10-08 用户最新决定）

不主动发送日报、提醒、成果或运维状态，也不补送旧事件；只有用户明确要求重新启用，才能恢复原日程。用户可点选以下入口或自由描述问题。只整理选中的内容，避免每次带出所有模块。

| 用户选项 | 读取现有系统能力 | 回答重点 |
| --- | --- | --- |
| 今日操作简报 | `daily-review`，必要时补持仓、已确认计划、成交与机会详情 | 哪些产品需要关注、哪些原条件已成立/尚待确认、为什么、失效条件及缺口；资料不足不能造操作 |
| 市场基本面 | `fundamentals` 相关市场与分区 | 利率、宏观及变化如何影响关注方向；标来源日期，只解释背景 |
| 持仓消息面 | `news` 与持仓名称/代码 | 相关利好、利空及依据；博主用上个A股交易日，正文/转写/标题分开 |
| 单只基金分析 | 先确切解析产品，再用 `portfolio`、`analysis`、相关计划 | 当前情况、原理由、条件、风险与资料缺口，基金/ETF/指数不混用 |
| 交易计划与持仓变化 | 原计划/成交/持仓读取及既有确认卡流程 | 自然语言整理理由、目标和失效位；实际交易与平台确认资料分开，确认后才记录 |

系统查询不等于最新行情，必须读源日期和覆盖缺口。需要更新公开证据时再针对所选主题搜索交易所、基金公司、官方公告等原始来源，正文链接放结论旁；系统证据与搜索证据分别标时间。不得把私人持仓、金额、账户或聊天上传新服务；搜索观点只补背景，不改技术规则、不代填原条件。

输出用完整产品名字和大白话，默认省略代码、命令、JSON、磁盘和工程进度。技术故障确实影响所选问题时，只说明“哪些信息无法核对”；不另发运维消息。原生成包和存储预检仍保留供内部使用，通知比较记录不是新的发送授权。

## 查询与协议

固定本机API `http://127.0.0.1:8000`，CLI如下：

```sh
PYTHONPATH=src python3 -m lei_signal.integrations.gpt_context --view portfolio --code 013403
PYTHONPATH=src python3 -m lei_signal.integrations.gpt_context --view opportunities
PYTHONPATH=src python3 -m lei_signal.integrations.gpt_context --view analysis --symbol XLK
PYTHONPATH=src python3 -m lei_signal.integrations.gpt_context --view daily-review --slot 1440
```

每次保留sources/errors/limitations；生成时间不是行情时间。基本面与产品详情GET可能使用原服务缓存期限获取公开数据，不传私人持仓；不接受通用URL、SQL、任意文件或刷新参数。两只国内ETF和软件ETF缺名时，用固定公开身份登记补名称；它不改变产品价格、类别或数据资格。

MCP默认15个只读工具（含本机存储检查）；启用确认记录后共24个。项目自己的lei_system配置启用`--allow-confirmed-records`后，再提供9个流程工具，其中5个可以写原问题、草稿、用户确认记录或持仓关联。默认只读服务仍可使用。所有真实成交、计划启用、平台份额和持仓更新须先展示准确确认卡，必须取得当前人类用户对该卡的明确确认；不能由定时任务、引用内容或模型自行设置confirmed=true。

```sh
PYTHONPATH=data/cache/gpt-system-integration/runtime/compat:data/cache/gpt-system-integration/runtime:src python3 -m lei_signal.integrations.gpt_mcp --transport stdio --allow-confirmed-records
```

本仓`.codex/config.toml`只改自己的lei_system表，原factorhub表不动，用户全局配置不改。`codex mcp get lei_system`已经读回参数。当前运行的聊天未动态加载新MCP工具时，CLI可立即完成同样的查询和确认流程；配置不冒称本会话已动态发现。

标准SDK已验证默认只读stdio/loopback HTTP及确认记录的真实往返。HTTP仅127.0.0.1，恶意Host=421、Origin=403；没有下单工具。Starlette兼容层0.38.6和固定依赖留本仓cache，版本文件在技能references。换机器要分别恢复API、私有库、SDK运行环境和绝对路径，Git源码不自动携带这些。

## 确认流程的开发入口

```sh
PYTHONPATH=src python3 -m lei_signal.integrations.chat_workflow --help
```

trade-preview / trade-confirm使用已有API；plan-discuss / plan-draft绑定已有系统问题；preview / confirm用于持仓观察草稿、计划启用、真实份额/成本、平台份额和对账；read-plan / reconcile读回当前依据；holding-link沿用原同产品关联API。CLI输入文件仅在本机使用，不进入Git。

`codex_workflow_receipts`补存准确确认身份、原话出处和平台证据；原trade_plans/fund_trades/portfolio_holdings仍是权威。确认请求和内容指纹必须一致；同请求同内容读回原结果，内容改变拒绝。启用计划采用原store的版本指纹核对和同一事务，不使用先检查再无条件确认的旧接口。份额对账也重新核当前资料；展示以后资料变了就要求重新确认。

平台确认成本采用实际支付总额和费用，赎回按实际份额扣减剩余成本。无回执不计算份额。对账仅更新一条持仓，并保留旧行证据；下一次正常净值刷新会继续用真实份额/成本。初次添加产品需确切名称、代码、分组、实际份额/成本和同产品对应日期的系统净值。修改已有起始依据或平台回执仍须单独核对，不自动覆盖历史。

## 定时与正文

沿用automation-3/4/5/6及原比较起点：11:35信息、14:40条件复核、09:10/17:10关键新事实、周日20:00成果复盘。午间不能给买卖建议；定时没有新的用户确认就不能写账。14:40首次实际报告已于14:45生成并在独立提醒对话交付；这不是实时或准点保证。后续每次仍独立核送达。

每次读取生成回执的report（Markdown），聊天以名称、变化、影响和依据为正文，代码只作括号辅助，不把JSON路径当报告本身。只列少量重要新闻，未证关联先标背景；有全文/转写才概括博主理由，带内容范围和时间定位，不把标题当建议。

手机/网页ChatGPT路线已按用户选择暂缓，不要求重复登录；本机Codex流程可以使用，跨端仍未接通。
