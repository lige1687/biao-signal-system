# T9：后来的新数据怎样改变已有判断，又不会事后改规则？（决策与架构，draft）

## 一句话结论（大白话）

**推荐：不建新系统。做法是“先把要观察的定义和预期写死并存指纹 → 之后每月人工核对一次新数据 → 每次核对只往一个只追加的记录文件里加记录”。** 这个记录文件格式和一个小校验脚本我已经写好并用 5 个合成情形跑通：等结果、结果成熟、输入被修订、定义出了新版本、观察预算用完中断，另有 3 个作弊情形（改历史记录、把冻结前的机会倒填进来、结果没到期就提前写）全部能被查出来。示例对象选 A03（“上涨中第一次回调是否比后续回调好”），因为它历史上已经给出“证据不足、方向不支持”，正好需要新数据来改判断；其他对象不换。没有启动任何真实观察：实际开始需要主负责人绑定合格数据和权限。

## 1. 两种方式比较

| | O1 观察协议＋定期人工核对，记录写只追加文件（推荐） | O2 在系统里加观察记录层（数据库表、定时任务、页面） |
|---|---|---|
| 能做到 | 冻结时点、全部机会（含不利的）、成熟结果、修订、版本切换、中断都有可核记录；改历史可被发现 | 同左，外加自动采集与展示 |
| 代价 | 每月人工跑一次；漏跑会留下缺口（如实记录） | 要改生产代码、调度和页面——超出本任务权限，且页面/助手接入已有负责线 |
| 风险 | 人工忘记核对 → 缺口；靠记录如实保留 | 自动任务“跑了很多次”容易被误当成证据变强；调度遗漏同样会有缺口 |
| 复用 | `workflow.py` 冻结合同与回执、定义登记表的版本号、`definitions.v1.json` 的 lifecycle 状态 | 需要新表与新接口 |

现有机制缺的只是一件事：`factor-evidence-reliability-usage.md` §1 明写“冻结观察生命周期”未接入；`breadth-freeze-observation-2026-09-09.md` §4–5 已有做法（输入观察与信号观察分开、取得时间和指纹、缺资料不补成当时信号），但没有通用记录格式。所以只补一个记录格式＋校验器，不补系统。

## 2. 交付物

- 观察合同草案：[observation-contract.md](observation-contract.md)。
- 最小记录接口与演练：`docs/experiments/raw/remote-astra-T9-2026-09-30/observation_ledger.py`（输出 `drill-output.json` 与 5 份 `ledger-*.jsonl`），5/5 与人工答案一致，3/3 负例被发现。全部为合成记录，协议指纹是占位符，没有读任何真实或未来行情。

## 3. 三件事分开表达

| 维度 | 由什么决定 | 例 |
|---|---|---|
| 资料质量 | 输入快照指纹、覆盖、修订记录 | “2026-11-03 那条最低价被修订，触碰仍成立” |
| 研究价值 | 只用已成熟结果、按冻结方法描述 | “新数据 3 次首次、2 次后续，只能描述” |
| 生产采用 | 另行授权，观察记录永远不自动推进 | 观察结论不写进规则账本或 OKR |

## 4. 证据限制

- A03 的冻结协议与运行目录 `docs/experiments/raw/a03-pullback-order-2026-09-30/` **不在 GitHub 快照中**（定义登记表的 lifecycle 依据引用了它）；本合同按 A03 报告和登记卡写，实际启动时须先取得原协议并核指纹。
- GitHub 快照里定义登记表的 178 条 lifecycle 依据中 56 条指向未同步的 raw 文件，`load_registry()` 在这台电脑上直接报错——这影响 T10，也说明观察启动必须在资料完整的那台电脑上做。
- 合同不保证观察多久就能得出结论；新机会可能长期很少。
