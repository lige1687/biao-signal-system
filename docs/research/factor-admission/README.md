## 一句话结论（大白话）

这套流程回答一个问题：**一个新指标凭什么能进因子库？** 答案是——必须先有一个
真实的研究问题（策略体系里某个具体决策需要什么信息），再证明现有的因子提供不了
这个信息，然后才允许以「候选」（大白话：只登记定义、还没验证过）身份登记进库。
准入流程**没有权力**宣布一个因子「已验证」或「可用」，那要靠另外两套既有规则
（F1 证据规则和 F2 证据链）逐步积累证据。

## 1. 核心原则：没有问题就没有因子

因子库不是指标收藏夹。任何候选指标进入登记表（definitions.v1.json）之前，
必须沿下面六个环节走完纸面流程，每一环都有书面记录：

```
研究问题 → 信息缺口 → 候选因子 → 定义登记（表单） → 证据要求 → 准入/拒绝裁决
```

- **研究问题**：候选先挂到《LEI 技术交易体系》或《LEI 技术实现》的具体章节，
  说明对应的决策或描述需求。挂不上时只能作为“体系外研究扩展”另作提案，
  不能冒充正式 LEI 因子；登记不等于获准纳入技术判定。
- **信息缺口**：说明为什么已有因子（在 `docs/research/definitions.v1.json`
  里逐一点名对照）提供不了这个信息。没有对照就没有缺口。
- **候选因子**：给出候选的初步定义（公式、输入、频率、单位、方向声明）。
  可以有多个候选，但每个候选单独填表单。
- **定义登记**：填写 `admission-form.template.json` 表单。**只写表单，
  不实际写入登记表**；实际写入是登记表维护动作，走 F1 字段标准，
  且写入后 lifecycle 只能是 `exists`。
- **证据要求**：引用 F2 Evidence Record 七阶段
  （definition → input_manifest → qualification → ranking_reconstruction →
  sample_ledger → blocked_report → independent_check），
  写明该因子若要升级到 `verified` 需要哪些阶段的什么证据。
- **准入/拒绝裁决**：准许登记为 candidate；或给出具体拒绝理由。

## 2. 与 lifecycle（F1）的对接关系

登记表 v1.3.0 的 lifecycle 四态：

| 状态 | 含义 | 谁有权授予 |
|---|---|---|
| `exists` | 定义已登记，仅此而已 | **准入流程（本文件）可产出且仅可产出这一态** |
| `verified` | 定义经过了函数级/数据级验证 | F1 证据规则（合成验证留痕、tests 等），准入流程无权 |
| `research_ready` | 可作为研究对象进入实验 | 研究合同另行授权 |
| `production_approved` | 可进生产 | 结构性禁止通过本线授予 |

两条硬规则：

1. **准入产出只能是 candidate（`exists`）**。表单里预填的 lifecycle 就是
   `exists`，任何人不得因「流程走得很顺」直接改写为 `verified`。
2. **`verified` 必须走 F1 证据规则 ＋ F2 证据链**：即提供 F2 模板
   （`docs/experiments/raw/factor-lib-f2-2026-09-19/evidence-record.template.json`）
   要求的七阶段证据，缺阶段用 `not_applicable` 显式声明，不许删字段。

本流程不造新状态、不造第二套登记表、不造第二套评估器。

## 3. 证据要求怎么写

准入表单的 `evidence_plan` 节按 F2 七阶段逐段写「需要什么、在哪里产生、
谁复核」。两种常见情形：

- **正常链**：七阶段全部可执行，目标（target）分析被资格墙阻断时输出
  "Evidence complete, Target analysis unavailable"，不算失败。
- **输入受限**：某些输入（如历史全A名单）缺失时，对应阶段记 `blocked`
  并给出 blocked code，同样不推翻 candidate 身份——candidate 只要求
  定义与问题闭合，不要求证据完成。

## 4. 拒绝的边界（哪些情况必须拒绝）

以下任一成立即拒绝，且拒绝记录入库防重跑（记录风格参照
`docs/research/methods/research-method-cases/` 的拒绝案例）：

1. **无明确研究问题**：指标存在但说不清服务于哪层哪个决策
   （「加个 RSI 看看超买超卖」不合格）。
2. **信息与已有因子重复**：与登记表已有对象逐一点名对照后，信息含量
   没有新增（换个算法定义同一信息不算新因子）。
3. **无法定义验证路径**：公式不可复现、输入主观、或没有任何可执行的
   F2 阶段安排，导致将来永远无法积累证据。

另有全局禁区（继承 F1/F2 裁决）：不按收益表现筛选、不按 IC 排名、
不自动淘汰已有因子、不生成交易规则、不改 trading-spec。

## 交付预检步骤（2026-09-20 起，advisory-only）

拟入库片段交付主控前，执行方先运行只读完整性预检并附结果：
`python3 docs/experiments/raw/factor-c-m23-2026-09-20/precheck_fragment.py <片段...>`
主控按既有规范核对发现项与未覆盖项（来源绑定/公式语义/证据适用性等仍由主控判断）。
**预检无发现≠片段合格；预检输出不构成自动合并或拒绝决定。**（方法来源：rmc-2026-09-20-c-m23-precheck-tool，GPT 采纳决定 APPROVED_ADVISORY_ONLY）

### 主控合并与运行前检查（2026-09-22，人工义务，不是新自动拦截器）

针对既往误改邻近定义、误运行读取真实行情脚本的记录，每批执行：

1. 派发前列精确可写路径；涉及定义时列 `id@version` 和允许变化字段。未列的对象/字段均保护，不能仅比较总卡数。
2. 记录原输入及相关源码指纹；主控合并后比较实际改变的对象/字段集合，必须与预计集合一致。出现外部并发变化先说明归属，不回滚他人修改。
3. 运行命令前检查入口及其导入是否会读取行情缓存、发网络请求或写结果。名称含“verify”不等于纯结构检查；仅人工输入的合同不能调用真实资料入口。
4. 固定测试文件和人工夹具路径；已知失败单独报告，不加容差或换容易通过的夹具。预期失败不算已修复，意外通过也须复查原因。
5. 记录实际模型/强度、派发/返修次数和耗时；token/费用不可得写未知。不能凭“便宜模型”或取消复核来宣称省钱。

本段不改变定义、数据用途资格、已冻结实验或生产权限；也不声称工具已自动执行上述全部检查。

### 先复用再开发（2026-09-22，用户明确的建设取舍）

每批新增能力前，在原任务合同中补一小段，不另建审批平台：

1. **要回答什么问题**：点明 ETF/宽指研究或 Agent 调用需要的具体输入、计算或结果，不能以“多接一个工具”为目标。
2. **已有东西能用多少**：先查仓库现成函数/API，再查最相关的一个外部工具；能直接调用就不复制实现，只缺格式转换就只补转换。
3. **是否真的可用**：分别记“看过资料、运行过小例、数值与含义核对过、接入了调用方”。列版本、缺失处理、输入时间、许可/成本和失败行为；文档示例、HTTP 200、供应商成绩都不能代替验证。
4. **何时允许自己写**：说明具体不匹配或成本理由；不因工具名字不同或已有局部代码就排除复用，也不为采用外部库推翻已经核实的本地定义。
5. **这批必须交什么**：交一个具体能力的采用/不采用结论与证据，或明确唯一待补问题；不无限扩工具名单。必要的独立小算例用于核对，不做第二套生产引擎。

这项人工检查不改变旧合同、准入状态和执行授权。最新有限评估见
[外部复用复核](../../experiments/factor-reuse-refresh-2026-09-22.md)。
