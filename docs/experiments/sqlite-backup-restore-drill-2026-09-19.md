## 一句话结论（大白话）

我们给数据库的"保险柜"做了一次小规模演习：先用 SQLite 官方的在线备份功能
（备份时数据库可以继续正常记账）把一个几百 KB 的测试小库复制了一份，再把这份
备份放到另一个独立文件夹里"还原"出来，然后逐条核对里面的记录——结果完全一致，
数据库自检（integrity_check，相当于体检报告）也是"ok"。这证明了**备份和还原的
操作方法本身是对的、能跑通**。但要说明：这次是在同一块磁盘上的小测试库做的，
它**不能**证明那台 3.3G 的真实数据库一定备份成功，更**不能**证明硬盘坏掉后
数据能救回来——那需要把备份放到别的机器/磁盘上，并单独安排真实库的演练。

## 测的是什么、怎么测的

1. **建测试库**：用系统真实建库代码（`sqlite_store.connect` 的编号迁移，WAL
   模式，与生产库同一套表结构）在临时目录建源库，灌入 3 条代表性事件行
   （密集突破 / A 回调 / 关键性波动，覆盖不同标的与方向）。
2. **在线备份**：用 Python 标准库官方接口 `sqlite3.Connection.backup` 备份。
   备份进行中从另一条连接**并发写入**第 4 条事件——验证在线语义：源库被改动时
   备份过程会自动重做，最终快照**包含**这条并发写入（是备份完成时点的一致快照，
   不是备份开始时的旧样子）。
3. **恢复**：把备份文件复制到与源库严格隔离的 `restore/` 目录，以只读方式打开，
   用系统自己的查询函数（`sqlite_store.count_events`）核对行数、逐行读回 9 个
   关键字段（event_id、标的、发生日、可用日、规则、方向、级别、强度等）与源库
   比对，并执行 `PRAGMA integrity_check`。
4. **缺失窗口演示**：备份**完成后**再补写一条"迟到事件"，确认它**不**出现在
   这份备份里——即任何备份都只保护到备份完成那一刻，之后的写入要等下一次备份。

## 实测结果（2026-09-19，本机 macOS，Python 3 标准库 sqlite3）

| 指标 | 结果 |
|---|---|
| 灌入种子行 / 备份时点源库行数 / 恢复库行数 | 3 / 4 / 4（含备份期间并发写入的 1 条） |
| 备份耗时 | ≈0.0017 秒（KB 级 fixture，仅证明机制，无性能参考意义） |
| 恢复（复制+只读打开+校验）耗时 | ≈0.0015 秒（同上） |
| 关键行逐字段比对 | 完全一致 |
| PRAGMA integrity_check | `ok` |
| 备份期间并发写入是否进入备份 | 是（在线备份语义成立） |
| 备份完成后迟到写入是否进入备份 | 否（符合缺失窗口口径） |
| 幂等重跑（含 --keep 目录重跑） | 通过，重跑前清空子目录，不残留 -wal/-shm 脏状态 |

## 口径与边界（哪些结论不能扩大）

- **数据缺失窗口**：每次备份只保护"备份完成那一刻"之前已提交的写入。备份期间
  正在写的行会随备份自动重做而被包含；备份完成后新写入的行只能等下一次备份。
  生产上这意味着两次备份之间的写入存在丢失风险，备份频率=风险敞口（保留策略
  与频率属用户待决，本单不制定）。
- **在线语义**：`Connection.backup` 读的是源库的一致快照，源库可继续读写，
  不需要停机。WAL 模式下备份得到的文件是完整独立映像（不需要伴随的 -wal 文件
  即可打开），本次已由恢复步骤实证。
- **是否离机：否。** 本演练源库、备份、恢复目录都在**同一块磁盘**上。它只证明
  "备份 API 用法正确 + 恢复流程能跑通 + 恢复后数据可读且自检通过"这一机制成立，
  **不证明生产库（3.3G `~/.lei_signal_lab/lab.db`）可恢复，更不证明磁盘损坏、
  机器丢失后可恢复**——那需要把备份复制到另一台机器/存储介质并定期演练。
- 真实 3.3G 库的备份耗时、锁行为、磁盘占用均未测试（非本单目标，等磁盘空间
  与用户授权另行安排）。
