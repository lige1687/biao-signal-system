## 3. R2 证据的准确范围

原材料 `R2-EVIDENCE.json` 明确记录：

| 原问题 | 实际计划 | 状态 |
|---|---|---|
| #52 | `plan_516220_SS_20260913114346_518bdfa6` | draft |
| #54 | `plan_516220_SS_20260913114810_dc2d2dc2` | draft |

两张计划属于不同会话，不能写成同一张计划从 #52 变成 #54。#54 的确认失败记录与历史截图属于第二次流程。

保存返回201、绑定落库、422拒绝有对应材料；但以下陈述不能采纳为已通过：

1. **“刷新后卡片恢复了同一已保存计划身份”。** `r2_plan_flow.py` 只断言卡片包含 `516220`，没有比对恢复后的 `plan_id`。截图确实显示原问题 #54，却又是“保存草稿”可点击、“确认生效”禁用。当前 `PlanDraftCard` 的 `planId` 是初始化为 null 的本地状态；历史接口虽提供 `plan_draft`，两入口没有把绑定交给该卡片。因此确认的是原问题内容恢复，不是已保存状态恢复。数据库中的绑定仍在，不等于页面已消费。
2. **“当前前端任何计划都无法确认”。** 应限定为“当前详情表单新建路径固定提交1.3.0，在当前2.1.0下被拒；所测会话草稿因早期转强规则被拒”。主控合法合成对照确认接口返回200，不能推广为所有来源、所有计划都失败。
3. `r2c-complete-plan-armed.png` 文件名不代表成功；同目录 `r2c-run.log` 明确写 `complete-plan-confirmed: FAIL`、请求409。结论按响应和状态，不能按文件名或脚本进程退出0判通过。其脚本未将所有失败传成非零退出，下一任务须同时保留结构化逐项结果与准确退出码。

这些修订由本主控报告直接纠正，不要求执行者再开一轮仅为改交付措辞的返修。

## 4. 下一任务的架构裁决

服务策略 §9 入场、§13 事前完整计划、§14 确认后纪律；只修计划流程。
