# 用户目标与首要验收：围绕标的、有系统依据的交易讨论

2026-09-07 用户明确目标。本文是产品目标的最高优先输入，修正前面“定投问答优先”的排序；权限仍沿AGENTS与总控决定，不改自动交易、排序或技术判定边界。

## 1. 用户要的主要能力

用户围绕一个标的提出任何与交易有关的问题，Agent应先查该标的现有回测与当前系统状态，整理潜在机会和风险，并结合基本面、情绪面的资料解释。证据不足且已有方法可复用时，可以现场补充该标的回测。用户认为值得继续后，再讨论资金、仓位、入场、退出，逐步形成完整、可确认、可跟踪的交易计划。

成功不是某个接口上线或定投卡片可见，而是用户能沿着同一标的连续追问，每一步都有对应证据，最终形成前后一致的计划。没有现成回测的标的也能明确知道缺什么、能补什么、补完回答哪个问题，而非只得到“暂无数据”。

## 2. 另一个独立功能：主动发现机会

用户尚未指定标的时，基于已有情绪研究、市场宽度和系统技术形态触发，从既有观察范围整理值得讨论的机会与风险。宽度指股票站在对应均线上方的比例。

主动发现不等于要求情绪、宽度、技术三个条件同时通过，也不擅自合成新分数。各机会注明来源、触发条件、证据、数据日期和适用期限；点击后进入同一个标的讨论流程。既有推荐排序先保持；任何排序与过滤改变另按用户既有边界处理。

## 3. 总控确定的对话流程

| 阶段 | 用户可能问什么 | 系统必须做什么 | 保留什么 |
|---|---|---|---|
| 标的概况 | “这个标的最近如何？” | 明确对象与数据日期；读取道路、路牌、现有触发、基本面和情绪；主动列潜在机会与风险 | 标的ID、当前状态、来源、证据缺口 |
| 依据追问 | “为什么这么看？历史胜率如何？” | 匹配本标的及相关模块、入场/退出方式、条件、期限的历史结果；说明有多少样本、盈亏幅度与不利情况 | 每项主张对应证据和适用范围 |
| 补充检验 | “没测过的话测一下”“换一种退出会怎样？” | 已有方法的同标的复跑可按需启动；先固定当前问题与参数，再运行、保存并回填结果 | 问题、数据和规则版本、run_id、结果及限制 |
| 机会讨论 | “这个机会值得继续看吗？” | 解释已满足、尚未满足、潜在触发、失效条件及风险；未来条件尚未触发时明说 | 当前事实与未来情景分开 |
| 资金与仓位 | “合适的话用多少资金？” | 在用户愿意继续后，读取其资金用途、预算、持仓与既有仓位规则，讨论可承受风险和方案差异 | 用户输入、约束、选择及来源；金额未定则保持未定 |
| 进入和退出 | “何时进、何时退？走坏怎么办？” | 用同一策略逻辑明确触发、失效、退出与备选情景；变更退出方式时同步更新证据，不能借旧成绩 | 同一版本的入场、退出、费用与证据 |
| 完整计划 | “把它整理成计划” | 将此前讨论整理为待确认计划，原规则与资金讨论可追溯，确认后按已有流程监督 | 确认版本、有效期限、来源与后续观察记录 |

“每个问题有依据”不意味着每个回答都硬报一个胜率：当前事实引用实时数据，历史概率引用匹配的回测，无法检验的解释明确标为解释或假设。用户仍可讨论尚未出现的机会，不必为了进入讨论先存在可交易信号。

## 4. 胜率和组合证据怎么用

1. 本标的、同一策略、同一入场/退出与评价期限的证据优先；不同对象或不同规则的统计只作明确标注的参考，不冒充本次机会胜率。
2. 至少保留symbol、module、entry_variant、exit_variant、condition_definition、holding_horizon、rule_version、data_window、fees、sample_count、source_run_ids。若原材料缺字段，标兼容性未知，不猜默认值。
3. 一起展示历史胜率、平均赚亏幅度、典型不利情况与样本量。胜率高但少赚多亏不能包装成好机会；近期和长历史分别看，不默默只挑较好窗口。
4. 技术、基本面和情绪可以综合解释机会与风险。只有同条件组合实际回测过且历史数据当时可得，才报组合的历史胜率；否则分别报已有统计并说明组合缺证据。
5. 基本面和情绪资料的解释价值不以是否参与技术判定为前提。可以检验历史分组差异，但不把当前财报倒填历史、不把消息在事后才公开的内容用于过去交易、不因叙事自动改原信号。
6. 单次现场补测回答当前问题，不自动成为通用规则或生产有效性标签。新组合、新阈值和更换研究方法属于新研究，由总控设计后再交执行。

## 5. 现场补回测的架构决定

优先复用 `copilot/winrate.py`、`plans/llm_context.py`、`api/routes/agent.py` 和现有 `/api/backtest/runs` 后台任务；不重做引擎。

证据查找顺序：同标的精确方法/版本结果 → 可明确说明差异的本标的历史结果 → 标明只是参考的其他对象结果 → 证据缺口。精确匹配与参考必须在响应中区分，不能把有一份module统计就视为当前问题已回答。

补测闭环：明确缺口 → 固定已有规则与数据截止 → 复用已完成兼容结果或提交单标的后台任务 → 展示正在补哪项 → 完成后回填原问题及原会话 → 保存引用。长任务不阻塞已有事实/风险说明；切换标的后结果仍归原问题，不串到新标的。

按需补测只运行当前问题所需的既有配置，不自动扫大量参数寻找最高胜率，不因为结果不好反复更换条件。缺数据、零交易、失败、样本少分别说明。若无法回答，指出缺哪类历史资料或研究定义，而不是把其他标的结果填进来。运行资源限制由总控在实施设计中按现有服务能力确定，不凭空承诺几秒完成。

## 6. 现状核查与真正缺口

已有：`agent.py::_prepare_discussion`会注入`winrate_for(symbol)`；讨论上下文已有新闻/事件、情绪及计划；回测API可后台发起并保存run_id。

待总控解决的关键设计：

- `winrate_for`当前只按symbol/module查成绩，返回未完整携带入场/退出/版本/来源run；需建立“这份统计是否回答当前问题”的匹配规则。
- `build_module_winrate.py`按symbol+entry_date去重后再分模块，且文件未保留完整来源配置；不同模块/退出方案混入或丢失的风险需核查。不能仅因有胜率表就把它称“当前机会的胜率”。
- 讨论里目前市场cold会写成`icepoint_active`，不能直接冒充该标的或板块满足完整四条件冰点；机会说明必须回到对象与真实条件。
- 多轮问题需要保留当前讨论的策略、入场/退出变体、证据缺口、补测任务、用户资金约束和计划版本，不能只保存聊天文本。
- 发现机会与标的讨论共享资料和计划链路，但入口与验收分开。

以上是本地静态代码核查；没有在本轮启动新收益回测或宣称其偏差已量化。

## 7. 第一批端到端验收（总控负责定稿场景）

1. 有匹配回测的标的：问现状→追问胜率→追问情绪/基本面→讨论资金→选择入场/退出→生成草稿，全程证据一致。
2. 无匹配结果但可复用方法的标的：显示缺口→后台补测→回填原问题；不拿其他标的统计冒充。
3. 修改退出方案：旧胜率不能继续给新方案背书；展示新证据或补测状态。
4. 只有市场恐慌、板块条件不齐：不得说该标的已出现完整冰点机会。
5. 有正反两面证据：同时说清潜在机会与风险，不只挑支持交易的事实。
6. 用户尚未决定参与：允许充分讨论机会，不提前要求资金金额，不建真实交易记录。
7. 主动发现入口：分别展示现有情绪/宽度/技术来源机会，点击后可接续上述讨论。

首要通过条件是“完整走通标的讨论并形成有依据的计划”，不是新建目录数量或定投问答命中率。01A、02基础修复继续；03改为本主流程的实现任务；04接完整计划；定投只作为资金用途之一。新收益研究05—08按是否帮助这个主流程重新排序。
