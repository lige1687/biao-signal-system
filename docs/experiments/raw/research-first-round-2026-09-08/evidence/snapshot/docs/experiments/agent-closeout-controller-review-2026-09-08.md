## 3. 独立反例：9 个场景，归并为 7 项返修

### Q1：实际规则版本不参与分组（P4/P7，阻断）

**复现：** 用真实 `journal.save_recommendation` 写入两天的同一标的，规则适配器分别提供 `fixture_v1` 与 `fixture_v2`。数据库中确有两份不同版本及摘要，汇总同期限却只有 **1 组**，期望 2 组。

**原因：** `observation.py:207` 的样本键和 `observation.py:1035` 的分组使用兼容字段 `rule_refs`，真实封装填的只是相同文件路径；新冻结字段的规则版本和配置摘要未参与。这不是缺字段，而是消费者仍读旧字段。scope 也未进入汇总维度。

**要求：** 用实际冻结规则的稳定身份与策略范围分组/去重；只有路径的历史值标未知，不默认与新版本可比。不要以整个引用 JSON 的展示文案或绝对路径作为策略身份。

### Q2：历史同步重读新规则，伪造新展示（P5/P7，阻断）

**复现：** 同一份情绪 JSON、同一 `content_hash`、同一修订键先同步一次。只让规则引用适配器返回新版本，再同步：主张 **1→2**、展示批次 **1→2**。新规则还被挂在旧 `emitted_at` 下。原行未覆盖，但凭空多出一次历史展示。

**原因：** `observation.py:549` 每次重建当前引用，主张身份包含该引用；批次 ID 又包含新主张 ID。稳定修订键没有独立约束来源事件身份。

**要求：** 重试恢复原事件的冻结依据；真实新展示才允许形成新事件。旧资料从未保存当时依据时应未知，不能在迁入时把今天的规则当历史事实。

进程内替身只改变真实适配器的返回版本/摘要，未修改真实规则文件。该场景专测消费者在上游材料更新时的行为。现有 `test_p7_material_update_creates_new_record_old_frozen_unchanged` 只把 `content_hash` 从 h1 改为 h2，没有更新证据材料，不能验证此性质。

### Q3/Q4：未展示内容与首次展示时间仍影响错误（P3，阻断）

**Q3：** A 已展示，再生成未展示的 B。当前成员从 A 变成 B，正式当前数量反而变为空，展示批次数变成 2。`record_observations` 建草稿批次也会更新 `superseded_by`。草稿应留档，但不能替换用户实际见到的内容。

**Q4：** 8月3日生成但未展示，8月20日才展示；以8月4日为截止评价，仍产生8月4日 ready。虽然首次展示时间存了8月20日，评价器并不读取它。观察日不能替代预测实际给出时间。

**要求：** 当前集合与展示次数来自实际展示事件。首次展示时间必须进入前向资格和重放截止检查；展示前已经发生的结果只能是历史观察，不能算“事先说对”。不通过偷偷平移旧观察日修复，也不补造历史展示时间。

### Q5/Q9：迁入接管当前版本，并把未知归属当可靠（§6，阻断真实迁入）

**Q5：** 真实封装已有当日实时记录，运行临时库 backfill 后当前集合变成 legacy 主张；实时批次被标已替换。迁入还把当前运行时间填入旧记录的 `first_shown_at`。这直接违反 v1.2“旧数据迁入不接管实时当前版本、旧记录不能补造展示时间”。

**Q9：** 使用本仓 HEAD 旧 `journal.save_recommendation` 原函数：先存卡片与成绩，再改同标的理由重新存卡片。旧代码只覆盖 payload，不清除 outcome；两种 hash 都没有。新 backfill 把这份已无法证明归属的 99% 成绩作为 legacy ready 挂上当前卡片，评价日还是 null。

旧源码完整存于 `legacy_journal_HEAD.py`，对应提交在 `legacy_source_commit.txt`；并非仅靠假想数据库坏状态推论。`outcome_payload_hash is None` **不能证明“旧行未被替换过”**。原文与旧数字必须保留，但应按归属未知隔离，而非强挂新卡、参与可靠成绩比例。

**总控纠偏：** 我此前探针 F 验证了旧数字是否可见，没有验证其归属是否可证明。它通过不能覆盖 v1.2 §6。新验收须要求“旧原值可查且未知归属不计可靠成绩”，允许修正旧 F 中过强的 ready/计数断言；不能为保持旧断言全绿而保留错误迁挂。

### Q6：情绪脚本仍有第二套混算成绩（P4/P8/P10，阻断）

**复现：** 同一天同一标的两份措辞修订，加一条 legacy 记录。SQLite 正确返回实时 1 样本、legacy 独立 1 样本，脚本 `review(save=False)` 却输出“到期3个、方向命中3个”，未隔离 legacy。

**原因：** `sentiment_journal.py:395` 仍按 JSON 中每条 review 直接追加收益，不用统一的样本、版本、来源质量规则。新表正确不能抵消旧用户可见出口错误。

**要求：** 正常输出、无数据库降级、只读重放均使用同一统计规则；无法确定样本/版本时显示未知和原记录数量，不回退为另一套胜率。补测已保存未来成绩过滤，且不可修改生产历史成绩。

旧 journal 现有重放测试只验证“保留已存未来结果”，没有验证带截止的读视图。保留数据库历史是正确的；读取时仍须按请求截止筛选，两者不能互相替代。

### Q7/Q8：错误隔离只完成在下游（P5/P9，阻断）

**Q7：** 情绪 JSON 第一条 dict 缺 date，后面有正常记录；从真正的 `review(save=False)` 进入即 `KeyError: 'date'`，还没有走到已修好的 `_sync_observations`。

**Q8：** picks 内有记录但缺 code，同步过滤后变空，返回“已同步1条”，并记成“零触发1天”。无法识别标的不等于确认当天无信号。

**要求：** 输入校验覆盖 record/review→同步→评价→输出全链；区分空组与坏组，错误数量及原因可见，正常对象继续。不要把不可解析输入变成成功空结果。
