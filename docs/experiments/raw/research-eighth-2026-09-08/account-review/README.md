# 第八批技术账户：独立逐日资金复核 · 2026-09-08

## 一句话结论（大白话）

8种方法的33,592条日账已用另一套算法从头重建，现金、持份、分红、费用、每日财富及排除新入金影响后的涨跌全部对齐，没有发现剩余记账错误。汇总里“多久未回到原高点”的首版计时错误已由主研究修正，本复核也独立确认新数字正确。这只说明给定买卖的账算对了，不代表哪种方法适合实际采用，或完整B已经实现。

## 如何做到独立

接受主输出前先写`protocol.md`并冻结核算程序。本复核不导入主账户引擎、不调用第七批价格转换器、不调用Spark指标函数。采用40位十进制数，从固定名义行情、已核基金行动、每周一各产品250元入金，以及实际成交表逐日计算：

1. 分产品重建现金、持份、末次已知价格和日期、登记权益、应收及支付。
2. 根据自己的持份在收盘估值；外部入金按前一日投资净值增加账户单位，避免把新增收入当收益。
3. 独立累加费用、现金和资产，再核主日账的总账户及每个产品字段。
4. 每笔成交另核名义开盘、禁止日期、普通日开盘限制、整手、现金、买卖日期隔离和P7风险预算。
5. 每个持仓独立汇总累计买入、卖出、费用和股息，闭仓与未结束分开。

主输出、协议及补充、候选CSV、源行情/事件接口和接受的主引擎原件保存在`accepted/`。`accepted-inputs.json`冻结63份文件。被接受主引擎SHA-256为 `e9ac99086c25def3774782d5f4632b58060618b0038cd0a9064c8bfe1a40a682`。主引擎只作为版本证据保存，不参与本复核计算。

## 容易算错的边界

**P6重复买入。** 不是只验最终份额。本复核在每一个可用开盘，依据自己的可用现金、当日开盘和0.1%买入费用，重新计算最多可以买的100份整数手，再和成交表比较。1,907次买入与所有未买日期均一致，没有漏买、超买或把多次买入当多份互相重复的持仓。

**无价拆分。** 2022-01-13的513100没有可成交报价，P6持份仍由39,700变198,500，旧估值由5.192变1.0384，乘积不变。报价来源日期保留2022-01-12，不能把换单位后的估值当1月13日新报价。1月13日及研究保守略过的1月14日均无成交。

**P7预算。** 用前一民用日产品财富的1%，没有算入当天新款，也没有误用每单位投资净值：

| 买入日 | 前日产品财富 | 1%计划风险金额 | 仅由风险允许的份额 | 实际份额 |
|---|---:|---:|---:|---:|
| 2018-11-23 | 50,750.0000 | 507.5000 | 56,300 | 18,500 |
| 2021-12-14 | 90,556.6195 | 905.566195 | 28,200 | 25,100 |

两次都是现金限制先约束数量，所以P7这条实际路径和P4相同。不能由此推论风险预算在更多机会中永远不起作用。实际入场水平线还按独立公式，从原候选信号日迁移到成交日后检查，潜在盈利与预设亏损比例均达到3。

**分红与期末。** 每次现金权益从本复核登记日实际持份计算，除息时记应收，付款时才转现金，股息归回原持仓。期末8条账户路径的应收均为零，不是强行把非零应收清掉。P6四只产品的持仓保留真实末价估值，没有虚构卖出、扣卖出费用或计入已完成交易胜率。

真实路径里，技术持仓均已结束；没有发生“技术持仓卖出后才除息”的实际案例。因此本次真实账不能宣称已证明这类边界在所有情形正确。主引擎已有另行合成反例，而本次独立结论只覆盖这些真实事件和持仓；后续新增场景仍需保留对应测试。

## “多久未回到原高点”的独立修正确认

这里计算的是**排除新增收入影响后的账户投资净值，从最后一次达到或超过既往高点，到恢复或研究期末之间的民用日数**。与某一笔持仓买了多久不是同一个指标。净值平着走、每天都等于旧高点时，要把高点起始日期不断移到最新一天，不能把之前几年的全现金等待也算作已经下跌。

主研究首版汇总在这个平高日期上处理错误；主研究已保存旧版和修正记录。本复核另冻结这两版汇总及相关版本证据到`accepted-summary/`，直接使用**自己的独立每日净值**重算，没有调用修后的主函数，全部确认一致：

| 配置 | 正确最长天数 | 该段起止日期 | 该段是否恢复 |
|---|---:|---|---|
| P0 / P1 | 0 | 没有下跌区间 | 不适用 |
| P2 | 1,660 | 2021-12-13—2026-06-30 | 未恢复 |
| P3 / P4 / P7 | 2,777 | 2018-11-22—2026-06-30 | 未恢复 |
| P5 | 1,805 | 2021-07-21—2026-06-30 | 未恢复 |
| P6 | 1,527 | 2015-06-14—2019-08-19 | 已恢复 |

P6最长区间已经恢复，但期末另有2026-06-02开始、尚未恢复的短段，两个结论不矛盾。2015-06-14是星期日，它是当时与旧高点相等的最后一个民用日，因此按本次定义更新起点。

技术持仓全部卖完后，剩下现金不计利息；以前损失不会靠继续等候自动恢复，新的外部入金也不抬高投资净值。因此可能只有很少几笔买卖，却留下多年的未恢复记录。不能把这段时间误读成一直持有同一份基金。

此次修正只改计时汇总；接受的40份账户五表指纹始终未变，账户盈利和最大跌幅没有改变。详细证据在`recovery-checks.json`及`accepted-summary/summary-correction.json`。

## 结论边界与交付

确认的是既定成交的资金处理、成交价格/限制、数量和汇总计时。候选是否符合正式策略、何时应触发退出，由主研究与另一候选复核负责，本包不重复冒充完整策略实现验收。完整历史公司行动、日内成交可得性、用户真实资金费用、未实现纪律仍不因本次对账通过而补齐。

- `verify_accounts.py`：独立十进制重建；`results.json`为8配置核对摘要。
- `reconciliation/`：全部33,592行独立日账及每行差值。
- `events-reconciliation.csv`、`roundtrips-independent.csv`：每条事件和每个持仓独立核对。
- `check_orders_and_boundaries.py`与`order-boundary-checks.json`：全部订单、P7、P6和拆分边界。
- `check_recovery.py`与`recovery-checks.json`：最长未恢复天数独立重算。
- `accepted-inputs.json`与`accepted-summary-inputs.json`：分别63份账户输入及4份汇总证据的接受指纹；`manifest.json`冻结交付。

复验时直接运行以上三个检查程序，不加`--freeze`，不会调用网络或主引擎。脚本只会更新本复核目录输出；若要保留本次所有时间戳，应先复制本目录。主五表发生变化需要建立新接受版本，不能覆盖此已封存结论。
