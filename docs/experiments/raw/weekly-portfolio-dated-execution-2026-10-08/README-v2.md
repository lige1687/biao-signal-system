# 带日期账本第二版：修复独审反例，待再次验收

## 一句话结论（大白话）

第一版虽然23项检查通过，仍能跳过已经到时的拆分或收盘账，并允许人工绑定的同日份额解禁；这会少记资产或把入金错误地当成收益。第二版已把这些必须完成的前置事项放到账本入口。11组相关检查通过，31次拒绝前后金额相同；仍只证明合成工程场景，不说明投资效果，也没有真实交易。

## 旧问题与证据保留

原四份源码准确保存在 v1-source/，指纹与 implementation-source-sha256.json 一致。第一版全部测试、金额、算术、README与validation回执未覆盖。v1-preserved-artifacts-sha256.json 用于核对旧证据完整性。旧README属于已被独审拒绝的第一版交付候选，当前判断以本第二版及主控独审为准。

独审最小反例在修改前实际运行了三个：

| 问题 | 第一版实际错误 | 第二版行为 |
|---|---|---|
| 跳过08:00到时拆分直接卖出 | 原100份×2元总资产200，误卖100份×1元后仅100 | 原子拒绝；补做拆分成200份，再卖100份，卖款100+剩余持仓100=200 |
| 跳过已绑定上一日收盘后入金100 | 错用旧单位价.2发行500单位，总单位1500 | 拒绝；补齐上一日300资产/1000单位=.3后，只发行100/.3单位 |
| 同一天09:30买入，15:00人工解禁再卖 | 买入、卖出都获接受 | 按显式Asia/Shanghai日历时区拒绝同日解禁的买入；没有新增例外参数 |

上述错误及具体资产、单位、日期回执见 v1-independent-failure-reproductions.json。三个错误都已在原第一版中确实复现；不是只根据文字推断。

## 入口修复

- 已绑定并到时的拆分或分红必须先执行，后续支付、成交、收盘或跨日事件无法跳过。相同时刻多个行动须给唯一整数sequence；没有顺序或顺序重复就拒绝，不能自己猜。按显式顺序逐项完成后才放行后续事件。
- 入金检查日历明确绑定、在当日本地日期前的最新应完成收盘，与账本实际保存的完整日账时刻一致。缺收盘或缺合法估值就拒绝，不造价格、不猜日历。
- 每笔买入的release_at在日历明确时区中必须晚于买入日期。即使文本时区不同，转换后仍是同一当地日期也拒绝；首次检查UTC写法与上海日期的反例。
- Group4直接断言两100份批次加10应收在拆分前390、拆分后390，两个release_at均不改变。后续合成开盘价2使资产810单列为价格输入变化，绝不叫拆分收益。

## 验证与失败记录

最终 tests-v2-final.json/log：7组新日期账本合同检查+4组独审修复检查，共11组通过。没有在最终运行重跑旧封存16项或迁移16项。第一次修复运行沿用了原runner，实际运行27项（含迁移16）并出现1个旧夹具跳过必要分红的错误；完整失败保留在 tests-v2.json/log。补上该合法路径必需的分红后，最终runner收窄到上述11组。没有修改拒绝条件或删除失败项。

event-step-money-receipts-v2.json 记录60步，29接受、31拒绝，每次都有执行前后的可花现金、受限现金、应收、份额、可卖份额、资产、单位与费用。money-receipts-v2-final.json 保存实际运行命令；原复制的记录器误标旧文件名，原记录仍保留，新回执明确修正标签且没有更改金额或再执行事件。

independent-arithmetic-v2.json 从保存金额直接独立重算20项，不导入账本实现。31次拒绝的before与after逐字段相同。入金单位数和资产精确核对；重复小数除法在Decimal的28位精度下产生1e-28净值舍入差，显式核对舍入限1e-27，不冒称无限精度。首次精确相等检查失败及当时算术源码保留在 arithmetic-v2-attempt1-failure.json、arithmetic_checks_v2_attempt1.py；账本没有为此改动。

四份第二版实现源码冻结于 implementation-source-v2-sha256.json。实际命令、各次退出码、源6、原v1小快照与证据保留情况、文件字节及空间检查在 validation-receipt-v2.json。

## 边界

具名日历、价格、产品许可、解禁与支付时刻、行动权益和同时行动顺序都是人工构造输入。真实产品日历、结算算法、公司行动覆盖、成交资格与行情仍未合格，本实现没有替它们作推断。P0/P1完整政策、订单求解、正式撮合、收益研究、生产与真实账户均未实现或授权。第二版仍须原独审者再次验收，测试通过不是最终接受。
