# H1/H2 执行代码静态审阅

日期：2026-09-08

## 一句话结论（大白话）

本批代码按冻结协议把每周信号放到下一周才交易，并沿用首12账户的现金、费用、分红和停牌处理；修正起点文字歧义和边界测试后，本次限定范围内未发现会阻止主运行的问题。

## 审阅范围

这是只读代码审阅，不独立重算8个新账户的完整资金结果，也不评价收益优劣。审阅对象是协议 v1.1、候选信号生成、通用账户适配、主运行入口、准备测试、候选信号文件，以及被复用的首12资金执行器。完整资金逐日复核由另一位执行者负责。

## 逐项结论

- **H1 精确界线与周状态：通过。** 代码直接比较 `3 × 宽度 <= 130` 和 `3 × 宽度 > 136`，状态从0开始，中间区域保持原状态。测试用有限十进制数检查两条无限小数界线的紧邻两侧，没有把 `43.33` 当成界线。每个有观察的完整周均发布当前状态。
- **起始周：通过。** 以 `eligible_date >= 2015-01-01` 筛选。2014-12-31观察、2015-01-05执行的首周可以进入；执行资格早于起点的旧周不会预先改变状态。协议 v1.1 已明确这是预期行为。
- **H2 当时已知的每日60日趋势：通过。** H2只读取周日结束前已经产生的每日趋势切换，周一及之后的切换不会倒灌。首12准备信号中的每日60日状态被直接复用，合成比例为宽度比例与趋势比例的较大值，且不超过100%。
- **先形成信号、后执行：通过。** H1记录保留该周最后一个有效宽度的来源日，例如首条为2014-12-31；它没有另存 `decision_date`，完整自然周周日可由执行资格日前一日推导。H2明确把该周周日写入 `decision_date` 和 `signal_date`。两者的执行资格日均为下周一，账户只有到执行资格日才创建订单，并在可成交开盘处理。当前冻结的589条宽度记录的执行资格日均为周一。
- **缺周与末周：通过。** 没有宽度记录的周不会凭趋势新增信号；旧挂单进入下一自然周前取消。2026-06-30所在未完成周的H1/H2两产品共4条记录单列为候选，没有进入账户信号。
- **分红和其他公司行动：通过复用检查。** 两个候选都映射到首12的周度5个百分点执行政策，并调用同一个 `simulate`。该执行器先处理拆分和分红到账，再处理当日信号与开盘交易；登记日持有份额、应收款和到账现金逻辑没有在适配层重写。
- **费用、份额和限制：通过复用检查。** 初始10万元、0.1%/0.2%单边费用、100份整数、名义开盘价、停牌与研究限制均来自首12冻结输入和执行器。运行入口限制为2个候选、2只ETF、2档费用，共8个新账户。
- **主运行锁：通过。** 运行锁逐一列出并固定了主程序、适配器、信号准备程序、门槛、候选信号、协议、首12模拟器、分红事件、成交设置、限制和两只ETF名义价格；运行结束复核16项均未改变。`price_basis.py` 没有被本次账户运行导入：它只在更早生成每日60日准备信号时使用，其结果已固化在 `prepared-signals.json`，而该辅助文件本身也由首12 `source-lock.json` 固定。因此它不是这次主运行的直接读取依赖，不能把它描述成本次分红记账辅助程序；本次分红记账直接由首12 `simulate` 和 `actions.json` 完成。
