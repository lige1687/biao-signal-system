# 纯订单规划第二版：现金、计划身份与行动资料修复候选

## 一句话结论（大白话）

第一版会把早先已经花掉的现金再次用来安排买单，且不同资金回执可能产生相同订单身份，后续还能忘掉原先已知的公司行动。第二版要求当前现金资料、为每份完整计划生成独立指纹，并强制继承原行动覆盖资料。9组针对性检查通过，13项独立金额计算和17份完整计划指纹重算通过；尚待主负责人独审，不代表策略有效或能实际交易。

## 先保留并复现第一版

第一版三源码保存在 v1-source/，与首版SHA相同；仓内原三源码、tests-01、原算术和所有首版回执均未改动。v1-preservation-sha256.json 保存准确旧产物指纹。README.md属于已被独审拒绝的第一版候选，第二版判断以本文件及主控复核为准。

三个旧错误在修复前确实复现，保存于 v1-defect-reproductions.json；恢复后没有重跑旧复现：

| 原问题 | 第一版实际错误 | 第二版检查 |
|---|---|---|
| 旧自由现金200已经用于别的已完成支出 | 当前只有卖款174.82，却按374.82安排300份，成本305.3，超用130.48 | 显式当前快照含卖款174.82，只安排100份、成本105.1 |
| 同一个原决定和目标开盘、不同实际卖款 | 卖价1.8与.5导致不同预算、数量和限价，却有相同order_id | decision_hash保持相同，plan_hash和order_id不同 |
| 原计划知道Jan6行动 | Jan2卖出合法，后续Jan7买入因遗漏actions参数错误放行 | 行动资料从原计划自动继承；跨已知行动返回unsupported，没有可省略的actions参数 |

## 必填输入与身份

新入口是 order_planning_v2.py 的 plan_p0、plan_p1、later_buys 与 validate_opening_order。第二版复用未改动第一版的整手数量、价限和预算算术，不复用有缺陷的旧后续现金函数。

CashSnapshot不可变，必须具名绑定当前可分配现金金额、来源ID、已知时刻、可用时刻，以及是否已经包含本次卖款。已经包含必须绑定准确receipt_id，原样使用金额，不再加卖款；没有包含，只把该次实际净卖款加到当前快照。绝不默认加旧决定的free。快照缺失、尚不可用或卖款身份不匹配均拒绝。

ActionContext不可变，必须具名绑定来源、已知时刻、覆盖起止和事件时刻。即使没有事件，也必须明确覆盖范围。后续自动继承原计划的同一context，不能用省略参数当作没有行动。目标开盘超过已确认覆盖范围返回unsupported_action_coverage_unknown；跨已知行动仍返回unsupported_company_action_crossing，不推断订单调整规则。

原decision_hash完整保留，另新增plan_hash绑定当前cash、实际资金回执、行动context、冻结及目标时点、状态/原因/排序/预算/余款和每个完整订单内容。order_id从plan_hash、固定序号、代码及买卖方向派生，因此不同现金来源、receipt、冻结时点或计划内容不会沿用同一订单身份。它是可复核内容指纹，不是交易所订单或预占记录。

## 新检查与核算

tests-v2-01.json/log 是9组新检查的实际运行回执，只检查三处修复、合法对应路径和受影响的纯算术，没有重跑旧15项、原账本或任何市场策略。synthetic-receipts-v2.json保存新输入、现金、行动覆盖和完整计划。

independent-arithmetic-v2.json 从保存资料重算13项金额、17份plan_hash及各order_id，不导入规划实现。实际结果包括：

- 当前174.82元只可买100份，成本105.1；不能用原free200凑成374.82。
- 当前快照不含卖款且金额0，加一次净卖款得174.82；若快照已含174.82，使用后仍174.82。
- 合法路径当前不含卖款200，加实际净款174.82得374.82，按原参考1买300份，费用后成本305.3。
- 同一原决定、卖价1.8与.5，预算374.82/244.95，数量300/200，限价1.231/1.198；plan_hash和order_id均不同，下一档价格都超各自预算。
- 现金缺失、现金尚不可用、错误包含回执、超出行动覆盖、已知行动跨越、同开盘资金复用、部分成交等均拒绝或明确unsupported。

三份新源码固定在 source-v2-sha256.json。validation-receipt-v2.json记录旧证据不变、新源码读回、实际命令、空间及文件大小。首轮第二版新检查没有意外失败。

## 磁盘失败与恢复

保存旧源码与复现后，第一次尝试写第二版时磁盘报No space left on device；立即读回证实order_planning_v2.py不存在，未发生半写。主控要求停止新增写入后，只读核对并报告恢复点。主控实际保存故障记录并核SHA b220831b7e1ca067ad5b25ed1bde038cd4ed15f79925ebfb3d74eca526b59732。

空间真实回升并收到恢复指令后，继续同合同；采用直接文件工具，每次写前实测、写后读回，测试日志先在内存收集再小文件保存，未清理或删除任何资料。空间波动原因未核，不把单次容量回升当永久保证。

## 边界

现金快照、卖出回执及行动覆盖全部是具名人工资料，本模块无法确认调用者漏报、虚构或实际资金是否真的存在；真实资料资格和已有执行接口仍须单独合同。这里只修纯规划计算与内容身份，不开发预占、部分成交、撤单、恢复、防重复执行或市场撮合。

公司行动跨越仍unsupported，触发却无整手可卖仍等待用户决定，失败卖单不自动追单。未修改策略、旧账本、真实账户、生产或研究参数；没有联网、获取行情、拟合或真实收益运行。源码与检查完成仍不等于独审接受。
