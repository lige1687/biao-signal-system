## 2. 三组固定补修（可直接交给执行 Agent）

请继续在上述分支修复，保留全部既有成果及修前证据。不要换模型、改规则、改真实业务库或另造架构；不要修改总控探针使错误变成通过。报告列明修前、修后、未覆盖，交回主控再决定合并。

### S1：断开时生成权必须有人负责收尾（高优先级）

**独立实测**：暂缓 `_enter_chat`，读取首条 `received`，关闭路由生成器，再允许后台真实登记完成。数据库 `answer_state=generating`；同一请求马上重试返回 `kind=incomplete`，而不是恢复生成。

**根因**：首条 yield 位于 try/finally 之前；且生成权只在消费者读取 `entered` 队列事件后保存在局部 `outcome`。消费者提前退出时，后台线程仍可取得生成权，没人释放。把首条 yield 移进 try 只能解决一半，不能解决后台晚领号。

**固定要求**：后台工作者与流消费者共用明确的结束/取消状态和生成权归属；工作者晚取得的生成权也必须收尾。清理仅释放自己的领取，不影响重试的新领取。无消费者后不继续启动新的解释生成。不能声称手动关闭 Python 生成器就等于验证了真实 HTTP 断开。

**验收矩阵**：

1. 回执后、领号前断开；随后允许领号完成，原请求可立即重试。
2. 领号成功但消费者未读 `entered` 时断开；同样收尾。
3. 准备资料期间、首段正文后断开；既有不重复问题和迟到隔离保持。
4. 旧工作者迟到完成/清理不得释放重试者的生成权，不新增重复问题。
5. 至少一次隔离 HTTP 服务上的真实客户端断开与重试；零付费模型，精确核对问题数、生成调用数与最终状态。

### S2：诊断包装不能改变数据库原行为（高优先级）

**独立实测**：启用延迟外键检查，在 `with conn:` 内插入不合法引用，离开时提交失败。原生连接自动回滚：`in_transaction=false`、未提交行数 0；`TrackedConnection` 却仍 `in_transaction=true`、未提交行数 1。实际后果是事务可能继续占锁。

**根因**：自行改写 `__exit__` 只调 commit；commit 抛错时没有保留原生上下文管理器的回滚处理。

**固定要求**：尽量让原生连接负责提交、回滚与异常传播，诊断登记按真实事务状态同步；不在跟踪层重新定义事务语义。与原生连接对照正常提交、块内异常、提交失败及异常类型/事务状态/行数。脚本、SQL COMMIT/ROLLBACK 和关闭后的登记不得残留或提前消失。

### S3：诊断必须区分等待、事务开启与已取得写锁（中优先级，本轮承诺项）

**三个独立反例**：

- `conn.cursor().execute(INSERT...)` 已开启真实写事务，但 `active_writers_snapshot()` 为空。
- 仅执行 `BEGIN`、尚未写入，已被登记成“持锁者”。
- 另一连接持锁时 INSERT 等待失败，失败的等待方仍出现在“活跃写者”中。

**固定要求**：不能在写语句执行前就把等待时间计为持锁时间；覆盖实际使用的 cursor/connection 写入口与事务结束入口。确实无法证明的状态标为“事务/锁状态未知”，不能写成持锁者。快照应能区分数据库，避免其他数据库的事务被当成本次锁冲突原因。用原生 `BEGIN DEFERRED`、失败写入、cursor 写入、显式提交、executescript 留未结束事务等构造测试。

报告必须删除“进程内快照为空就证明是其他进程持锁”的推论；空列表也可能来自未覆盖入口。批量化合成实验没有收益，只能说明该合成场景不值得改，不能证明历史 5 秒必然是排队等待。

## 3. 提速成果的采纳范围

- 向量化计算及两融历史短期缓存代码与新增测试有实际内容；主控独立重跑相关合成一致性与缓存测试通过。
