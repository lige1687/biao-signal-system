审查日期：2026-10-04（Asia/Shanghai）。范围为文献复核与静态检查；没有运行模型对比、付费接口或自动继续任务，没有修改现行规则或模型设置。执行状态：completed；证据：官方功能与文本问题可定位，实际节省费用未评估。

## 一句话结论（大白话）

更值得做的是让任务有明确终点、让 AI 只读当前需要的资料，并检查技能是否把小事强行变成多轮审批。继续堆“必须认真、反复检查、不能停”的文字，收益可能很小。我们已有按难度分工和验收规则，新增价值主要是规则触发范围、任务续做机制，以及按“完成一件合格工作总共花多少”衡量成本。没有证据支持宣称本项目已经节省某个百分比。

## 1. 官方资料带来的新增判断

- OpenAI 于 2026-09-11 的指导建议精简技能描述、按需要加载细节、避免对每次修改强制通读全部文档；它也指出过严的审批文字会让模型过早停下。对应本项目的推论是先审查触发范围和重复条款。[官方文章](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)
- Codex 的 Goal 是绑定当前聊天的持续目标：在任务尚未完成、目标仍有效且条件允许时可以跨轮继续；必须用实际证据判断完成。它不适合一句话修改或没有终点的“无限优化”。此前聊天把结束后的继续只归到自动化，说得不完整，应补上 Goal；本轮只确认文档及本会话工具入口，未启动或验证自动续做。[官方 Goals 指南](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)
- Anthropic 把缓存、减少无关输入、模型及思考档位、输出长度和任务预算分开讨论；选型应比较完成任务的总成本，强行缩小单次输出上限可能只增加失败，模型便宜也不代表整件事便宜。其内部结果不代表本项目效果。[官方成本指导](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)

以上是来源支持的结论；下文的具体安排是基于本地情况提出的建议，尚未实施。

## 3. 相对现有规则，哪些值得拓展

| 方向 | 现有基准 | 建议新增内容 | 判断与代价 |
|---|---|---|---|
| 长任务持续完成 | 已有三条结束检查 | 对路径不确定但终点清楚的任务，用户明确设置 Goal，绑定完成证据与边界 | 值得试用；属于运行机制，不能靠往 MD 多写一句自动开启，也不保证离线继续 |
| 技能的适用范围 | 有大量可用技能及通用强触发文字 | 描述写清何时用、何时不用；已给明确执行方案的小任务不反复进入设计批准流程 | 优先审查；现行用户指令优先，不能借精简取消真实授权要求 |
| 规则按需读取 | 根规则含策略、UI、研究归档、运维等 | 保留共同边界；细节按任务入口链接，避免无关资料全文重复进入上下文 | 值得整理；涉及策略的技术改造仍须按用户规定读取权威原文，不能自动削弱必读要求 |
| 工具返回内容 | 已强调按需取上下文 | 查询先限制目录、字段和行数；大表在本地计算，只回传汇总与证据位置；报错保留关键上下文 | 可作为执行习惯；过度截断会掩盖失败，不以短输出代替核验 |
| 选择模型与思考档位 | 已有按难度分工 | 有可靠验收的小任务可先测较低档位，失败再升级；重大方法与时点判断继续重视能力 | 先测，不默认低档；低档漏判失败会把质量损失隐藏起来，不自动改用户模型 |
| 多代理 | 已要求独立、必要才拆 | 派发只给问题、文件范围、输入和验收；每次评估协调及复核成本 | 主要是落实已有规则；多个代理的总消耗可能比单代理更高，不为省钱强行拆分 |
| 持续聊天与交接 | 已有短接续记录 | 同一任务沿用当前证据；独立新任务仅携带必要交接，避免长聊天混装无关任务 | 适合落实；过早切换会丢背景，不建议每一步都另开聊天 |
| 验收与简短交付 | 已有必要验证与大白话 | 每项验收绑定证据，变更使证据失效才重测；聊天给结果与关键限制，明细只留一处 | 不追加仪式；重要研究仍需完整核心结果，不能一律压成一句话 |
| API 缓存及批量请求 | 未检查本项目接入层 | 将可复用的重复输入交给服务缓存；不急于返回的独立请求才考虑批量执行 | 仅是 API 层候选；客户端套餐、缓存配置和账单未核，不能靠一句提示词开启 |
| 成本的衡量方式 | 目前没有本轮逐任务用量 | 记录完成率、失败重试、返工、耗时及可获得的用量；比较同类任务 | 值得建立小样本基准；不要先造庞大监控系统，字数变少不代表工作更省 |

采用优先顺序：澄清技能与记录触发范围 → 精简无关读取及工具输出 → 对复杂长任务试用明确 Goal → 在可靠验收下比较模型档位。缓存和批处理只在确实自建 API 调用时进入实施范围。

## 4. 怎样判断“真的省”，以及本轮没有回答什么

比较对象应是同一类任务、相同输入和相同验收条件。必须同时看合格完成比例、总尝试成本、返工和总耗时；失败尝试也计入总成本。只有拿到真实用量与适用计费口径，才能计算“总费用 ÷ 合格完成数”。若使用套餐且没有逐任务费用，就报告可取得的 token、耗时、重试和成功数，费用保留未知。

本轮没有运行跨模型比较，因此不能说某模型一定更便宜，也不能说这些建议已经使本项目成本下降。我们已完成的是官方依据与本地问题的对应检查；实际费用改善属于需要固定任务样本和运行授权的新检验。通用规则要服务所有会读取它的模型，模型特有的小技巧不宜成为所有模型必须执行的步骤。

不建议采用：任意给任务压很低的输出上限、全任务一律最低档位、默认多代理、每轮都全量测试、无限续做、自动购买额度、为了省 token 删掉权限边界或失败记录。
