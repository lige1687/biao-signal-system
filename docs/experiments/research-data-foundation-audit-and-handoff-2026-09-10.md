## 一句话结论（大白话）

**这是给复核用的总入口：五轮做了什么、我自己查出自己哪些地方错了、现在到底能用不能用。**

五轮的净成果是一句话：**我们现在能说清每份研究数据从哪来、什么时候取的、完不完整、
当时能不能拿到，而且每个结论都有文件和哈希可查。**

但更该看的是**自查结果**。这一轮我没有继续往前修，而是回头审自己前四轮的代码，
**五轮自查**：前四轮查出 17 个代码缺陷，第五轮查出 **5 处覆盖假象**（测试根本没在看的地方）。其中三处尤其该看：

> **一**：我声称那个"接受固有属性"的开关"不是放宽闸门的后门"，给了三条保证。
> **第三条有洞**——原实现只看"有没有可修缺陷"，不看裁决本身。
> 把一个阻断级问题标成"固有属性"，就能让"不可用"的数据被放行。**那正是我否认存在的后门。**
>
> **二**：快照记录价格口径时只取第一个标的的值。同一批里口径不同时，其余被**静默丢弃**。
> 而下游的"口径混用"检查恰恰是从快照读这个单一值——**所以那项检查永远不会触发**。
> 快照说谎，校验器信了，**两者一起对同一个风险失明**。

> **三**：快照里"允许用途"那段是我第一轮硬编码的，**不含"排序"**。
> 而我把"排序可以用"当头条结论写了两轮。**两套声明互相矛盾，两轮都没人发现。**
> 结论实质上是对的（那个硬编码列表本来就是随手写的），但它两轮里缺少产物声明的支持。

十七个缺陷都已修好并加了回归测试，修完结论没变（说明修的是真漏洞，不是推翻结论）。
另有 9 个疑点查证不是缺陷、1 项记录不修，都如实留档避免重复排查。

**四轮下来看清了一件事**：这些缺陷里有 7 个是同一个毛病——**某个字段由调用方口头
声明、从未与产物记录核对**。所以做了一处根治性改动：新增一个入口，
口径、币种、字段一律从产物自身派生，**函数签名里根本没有让调用方声明的参数**。

**第五轮又看清一件更要紧的事**：我前面每份报告都拿「N 项测试全过」当实现核验的依据，
但往代码里故意注入错误后发现，**至少 5 处的「全过」是空的**——那些逻辑坏掉根本没人知道。
其中一处（对象用途闸门）我甚至在第 1 轮报告里把它的正确行为当**证据**写过，却从未写成测试。

**现在的实际状态**：描述和诊断可用；排序和对照——数据缺陷已清零，只剩"产品池里 11 只是
评价期开始后才上市的"这个改不了的事实，研究者明确接受就能用；**归因仍然不能用**，
因为公司行动的到达时间和停牌数据本地都没有，得另外找来源。

**五轮都没有测任何因子，没有跑任何账户，没有任何收益结论，也不构成生产或交易授权。**

## 2. 自查发现的缺陷（本轮核心产出）

方法：不看自己的测试，直接对可疑点写探测脚本，看实际行为。
**共五轮自查：前四轮查代码（26 个疑点 → 17 个缺陷），第五轮换方向查测试本身
（注入 29 处错误 → 发现 5 处覆盖假象）。全部已修并加回归测试，另 1 项记录不修。**

> **命中率一路上升**：4/8 → 4/7 → 4/6 → **5/5**（50% → 57% → 67% → **100%**）。
> 我在第二轮后曾说"边际收益在下降"，**数据完全不支持这句话**。
> 这本身是个教训：不要凭感觉宣布搜索已经充分。
>
> 上升的原因不是运气，而是**第三轮起我锁定了一个模式去查**：
> 「某个字段由调用方口头声明、从未与产物记录核对」。
> 12 个缺陷里有 7 个属于这一类（G、K、L、N、S、T，以及 P 的哈希-结构脱节）。

> **一次探测脚本自身的错误也如实记录**：第二轮查"多标的时第一个失败"时，
> 我的时钟生成器超过 59 秒会抛 `ValueError`，导致我一度把测试壳子的报错
> 当成被测代码的缺陷。修好探测脚本重跑后，该项**证明无缺陷**。
> 教训：下结论前先确认探测工具本身是对的。

### 第一轮自查（8 个疑点 → 4 个缺陷）

### 缺陷 A（严重）——推翻第 4 轮的主张

| 项 | 内容 |
|---|---|
| 位置 | `data_quality.require_use(accept_structural=True)` |
| 现象 | 只检查"有没有可修缺陷"，**不看裁决本身**。把 `BLOCK` 级 finding 标成 `structural` 后，裁决为 `unusable` 仍返回 `conditional` **放行** |
| 为什么严重 | 第 4 轮报告明写"不是放宽闸门的后门"并给三条保证，**第 3 条有洞**——这正是我否认存在的那个后门 |
| 实际影响 | **潜在，未发生**：当时无任何 BLOCK 级 finding 被标为 structural。但主张写错了 |
| 修复 | `accept_structural` 仅适用于 `conditional`；裁决为 `unusable` 时一律拒绝 |
| 回归测试 | `test_structural_label_cannot_bypass_a_blocking_verdict` |
| 已加纠错指针 | 第 4 轮报告顶部 |

### 缺陷 B（中）——私有属性耦合

| 项 | 内容 |
|---|---|
| 位置 | `data_quality._check_against_calendar` 访问 `calendar._days` |
| 问题 | 跨模块读私有属性；日历内部结构一变，校验器静默失效 |
| 修复 | `TradingCalendar` 增加公开 `trading_days(start, end)` / `closed_days(start, end)`；校验器改用公开接口 |
| 回归测试 | `test_calendar_check_uses_public_accessor_only`（断言源码里不再出现 `calendar._days`） |

### 缺陷 C（中，但性质重要）——一个不可能失败的"核对"

| 项 | 内容 |
|---|---|
| 位置 | `symbol_identity.audit_mapping` |
| 问题 | `rows_after=rows_before` 是**硬编码**的。所以 `balanced` **永远不可能发现行数变化**——一个不可能失败的核对不是核对 |
| 对第 4 轮结论的影响 | 第 4 轮报告引用"映射前后行数 18,916 → 18,916"作为验证。**该项当时是空的**；但同轮我另外跑了 14 只逐只 `assert_frame_equal`，那个是真验证，**所以结论本身没错，是我指的工具名不副实** |
| 修复 | 增加 `mapped_frames` 参数：只有传入映射后数据才算核对过；不传则 `rows_after=None`、`rows_verified=False`、`balanced=False`（**不许假装核过**） |
| 回归测试 | `test_audit_balances_products_rows_and_dates`（含"不传则 balanced 为假"）、`test_audit_detects_row_loss_after_mapping`（故意少一行必须被抓到） |
| 副作用（好的） | 修完立刻挂掉 2 个旧测试——它们原本靠这个空检查通过。已改为传入第 4 轮实际生成的规范标签快照做**真**核对 |

### 缺陷 F（中）——第一手证据没被核验

| 项 | 内容 |
|---|---|
| 位置 | `data_snapshot.load_snapshot` |
| 问题 | 只核 `normalized/` 的哈希，**不核 `raw/` 原始响应体**。原始响应是第一手证据，被改动却不报，比标准化产物被改更危险 |
| 修复 | 逐条核验 `raw_responses` 的哈希与存在性，缺失或不符都进 `hash_mismatches` |
| 回归测试 | `test_tampered_raw_response_is_also_detected`（改一个字节必须检出，且测试自身 `assert tampered != original`） |

### 第二轮自查（7 个疑点 → 4 个缺陷）

### 缺陷 G（严重）——快照与校验器一起对口径混用失明

| 项 | 内容 |
|---|---|
| 位置 | `data_snapshot._build_snapshot` |
| 现象 | 用 `specs[0]` 取 `price_basis` / `currency`。同一批里若口径或币种不同，**第二个起全部被静默丢弃**，快照记成单一口径 |
| 为什么严重 | 下游 `check_prices` 的 `declared_basis` 正是从快照读这个单一值——**所以「口径混用」这项检查永远不会触发**。快照说谎，校验器信了，两者一起失明 |
| 与协议冲突 | 第 1 轮协议明写"不静默拼接不同价格口径"，实现没做到 |
| 修复 | 检测异构即抛 `AcquisitionFailed`（拒绝写入）；同时新增 `price_basis_by_instrument` 逐标的留痕 |
| 回归测试 | `test_mixed_price_basis_is_refused_not_silently_collapsed`、`test_snapshot_records_basis_per_instrument` |

### 第三轮自查（6 个疑点 → 4 个缺陷 + 1 项记录不修）

### 缺陷 K（**最严重**）——一句自由字符串就能让裁决变绿

| 项 | 内容 |
|---|---|
| 位置 | `data_quality.check_prices` 的 `calendar_authority` |
| 现象 | 它是**自由字符串**、无枚举校验。传 `calendar_authority="exchange_official"` 而**根本不给日历对象**，"无合格日历"告警消失，`ranking` 裁决直接变 **`usable`** |
| 为什么最严重 | 比缺陷 A 更容易触发：A 还得故意把阻断级标成结构属性，**这个只要编一句好听的字符串**。而且没有任何东西兜底（没有日历对象 → 覆盖检查根本不运行） |
| 与缺陷 G 同类 | 校验器信任一个自我声明的字段，不做任何验证 |
| 修复 | 引入 `CALENDAR_AUTHORITIES` 枚举；**声明任何非 `"none"` 的权威时必须同时提供日历对象**，否则报错 |
| 回归测试 | `test_claiming_calendar_authority_without_a_calendar_is_refused` |
| 副作用（好的） | 修完立刻挂掉 **22 个**测试——它们全都在用这句字符串当捷径消掉日历告警。已改为提供合成真日历，与生产调用方走同一条路 |

### 缺陷 L（中）——币种记了但没人核

| 项 | 内容 |
|---|---|
| 位置 | `check_prices` 完全没有 `currency` 参数，函数体也不提币种 |
| 现象 | 快照记录币种，**下游一个字都不看**。混用币种无人拦（不同币种的收益不可直接比较或排序） |
| 修复 | 新增 `declared_currency` 参数与 `currency_mixed` 阻断项 |

### 由此做的一处**根治性改动**

四轮下来，同一类缺陷出现了 7 次（价格口径、币种、日历权威、允许用途、字段、绑定前提）。
**逐个补检查治不了根**——只要还留着"调用方自己说"这条路，下一个字段还会出问题。

因此新增 `check_snapshot(loaded, ...)`：**口径、币种、字段一律从快照派生，
函数签名里根本没有 `declared_basis` / `declared_currency` 参数**，从结构上无法谎报。
`check_prices` 保留给需要故意传入不一致值的测试使用。

最终测量已改用这个入口（`final-measurement-v3.json`），结论不变。


### 第五轮自查：换方向——**检验测试本身**（变异检测）

## 5. 建议主控/上级模型重点复核的六处

1. **缺陷 A 的修复是否彻底** —— `accept_structural` 现在的三条件是否真的没有绕过路径？
   我自己已加测试，但这正是我上一轮自信写错的地方，值得独立再看一遍。
2. **"固有属性 vs 可修缺陷"这个分类本身是否成立** —— 我把"池非矩形"判为固有属性，
   理由是补数据改不了。但它也确实是个真实的研究陷阱（拿 14 只在只有 5 只存在的时期排序）。
   **把它从"降级"改成"可显式接受"，是否等于降低了标准？** 这是个策略判断，不该由我拍。
3. **日历只有深交所来源** —— 跨所一致性只核了 2026-02 一个月；发布时间证据来自上交所而
   逐日标志来自深交所，**两个发布方混用**是否可接受。
4. **发布时间证据的强度** —— 发布日期来自 URL 命名约定 + 正文落款，
   **不是接口声明字段**；且只覆盖 2026 年。以此支撑"2026 年安排自 2025-12-22 起可知"是否够。
5. **`announcement_date` 作为下界的用法** —— 我只做统计、不写入 `available_at`。
   这个边界是否画对。
6. **第 3 轮那 67 次请求的性价比** —— 日历补齐没有改变任何裁决。
   我在第 4 轮认为若先分类阻断项可以省下一部分。**这个排序失误值得复盘**。
7. **变异检测的 29 处也是我自己挑的** —— 29/29 被发现只说明「这 29 种坏法」会被抓到。
   建议独立补一批我想不到的坏法，特别是跨模块交互与顺序相关的。
8. **缺陷 G 揭示的一类风险是否还有同类** —— "产物记录与校验器读同一个被简化的字段，
   于是一起失明"。我只在价格口径上发现了它；同样的结构在别处（币种、日历权威、
   转换版本）是否也成立，值得独立扫一遍。
