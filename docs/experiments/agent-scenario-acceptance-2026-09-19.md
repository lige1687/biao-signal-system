## 一句话结论（大白话）

对助手问的四句常见话做了逐句体检：**「我的持仓需要关注什么」在真实网页上
全链路通畅**——能出持仓卡，账本为空时也如实说「暂无进行中的计划与基金持仓」；
**「这个买点为什么成立」和「美股科技弱对我有什么影响」两句话系统不会给卡片，
会转给聊天讲解管线**（按验收红线，这次没有真的让大模型回答，只核实了
「转讨论」这个路由动作真实发生）；**「现在能定投吗」发现一个真缺口**——
定投状态板这张卡在系统接口层是好的（一问就出卡、数据真实），但在网页聊天框
里打这句话，会先被一个更早的「问题分类器」截走转去讨论，**普通打字到不了
这张卡**；目前也没有任何快捷按钮能直达它。另外把三张新卡（定投状态板、
市场情绪速览、认知/心态卡）在真实网页上做了视觉走查：有数据时显示真实生产
数据、缺数据时降级话术全部如实出现。全程零代码改动、没有重启服务、没有让
大模型产生一次真实调用（4 次讨论管线请求全部被测试防护掐断）。

对用户的实际意义：**定投、情绪、心态这三张新卡现在「有但不容易到」**——
卡本身是好的，但网页入口没接上（详见缺口清单第 1 条，需要后续阶段决定
是否把入口接通）；持仓问答现在就能用；买点解释和跨市场影响这两类问题
本来就走讨论路线，不算坏账，但「转过去之后要等模型回答」这一段本次按
成本红线没有验证。

## 验收方法（双通道）

对每个场景同时取两路证据：

- **接口通道**：直接调生产后端的一句话分发接口 `/api/copilot/dispatch`
  （curl，原始 JSON 存 raw）；
- **页面通道**：真实 Chrome 无头浏览器驱动生产前端（vite 5173，独立
  浏览器 profile、不登录任何账号），在「AI 助手」抽屉里像用户一样打字
  发送，截图 + 逐条网络留痕（`browser-walkthrough.json`）。

红线落实：讨论管线 `/api/agent/chat/stream` 被路由拦截一律掐断（共 4 次，
明细留痕），**全程零次真实大模型调用**；缺数据降级态用 mock 注入（只对
文本含「模拟」或属 B 段三条探针的消息生效，其余请求原样放行），未动任何
生产文件；页面驱动全程只读。

## 页面链路的一个关键事实（先读这个再看四场景）

网页聊天框在把话送给分发接口**之前**，还有一道更早的统一预路由
（`web/src/utils/resolveRoute.ts`，调 `/api/copilot/resolve`）：只有被
分类成「报单 / 找机会 / 查持仓复盘」三种意图的话才进分发接口出卡；
其余一律转讨论管线。而分发接口自己的关键词表（`src/lei_signal/copilot/
intent.py`）里定投/情绪/心态都能命中出卡。**两层分类口径不一致**，
这就是下面缺口 1 的根源。快捷指令芯片（今天看什么/持仓速览/我要报单/
本周复盘）也走同一道预路由，同样到不了三张新卡。

## 四场景逐个记录（证据指针见 raw）

### 场景1「现在能定投吗」

- 接口通道：`dispatch-s1-dca.json`——命中定投意图，出 dca 直达卡，
  证据账本可用（版本 2026-09-08-r2）、中美宽度读数真实、11 个标的逐状态，
  HTTP 200。
- 页面通道：`02-s1-dingtou-page-realpath.png`——页面先弹澄清问句
  「这笔钱是持续投入的新收入，还是已有的闲钱分批？」，然后转讨论管线
  （被测试掐断，页面显示「未能完成」），**没有出 dca 卡**。
- 数据缺失降级：`07-dca-card-degraded.png`——「证据账本数据不可用…状态
  无法计算」+ 宽度行「数据不可用（健康度：未核实）」话术齐全（mock 注入）。
- 结论：**接口层直达卡成立（简报说「今晚已通」在接口通道核实为真）；
  页面自由输入到不了这张卡，为真实缺口（缺口 1）**。

### 场景2「这个买点为什么成立」

- 接口通道：`dispatch-s2-buywhy.json`——intent=chat、chat_fallback=true、
  话术「未命中快捷指令，已转通用讨论。」与 `intent.py` 词表逐一核对：
  该句确实不含任何命中关键词，路由事实与代码一致。
- 页面通道：`03-s2-buywhy-blocked.png`——页面经预路由直接进讨论管线
  （分发接口都未被调用），讨论请求被测试防护掐断，页面如实显示
  「未能完成：Failed to fetch」。
- 边界说明（如实记）：该场景属于讨论管线（`/api/agent/chat` 流式接口）
  覆盖范围，不在快捷卡覆盖范围内；按禁真模型调用的成本红线，本次只记
  「路由到了讨论入口」这一事实，**模型回答质量未验证**。

### 场景3「我的持仓需要关注什么」

- 接口通道：`dispatch-s3-holdings.json`——intent=holdings，出持仓卡；
  生产台账当前 active_plans=[]、fund_positions=[]（空仓）。
- 页面通道：`04-s3-holdings-empty.png`——**四场景中唯一页面全通的直达卡
  路径**（预路由分类为「查持仓」→ 分发接口 → 真实持仓卡渲染）；账本为空，
  卡内空态话术「暂无进行中的计划与基金持仓。」如实出现——这本身就是
  数据缺失时的降级表现，且是真实生产数据，不是 mock。
- 结论：链路通畅；降级话术验证通过。

### 场景4「美股科技弱对我有什么影响」

- 接口通道：`dispatch-s4-ustech.json`——intent=chat、chat_fallback=true
  （词表无命中），与代码一致。
- 页面通道：`05-s4-ustech-blocked.png`——同场景2，页面直接进讨论管线
  （被掐断），无卡。
- 边界说明（如实记）：跨市场传导当前无快捷卡、无已验证的传导分析模块；
  该问题由讨论管线承接，本次按红线未跑模型回答，**「美股科技弱→对我」
  的传导结论没有任何已验证产出**，不得当能力宣传。

## 缺口清单（如实，不粉饰）

1. **【页面入口缺口】三张新卡在网页聊天里「有但到不了」**：自由输入和
   快捷芯片都先过预路由（`resolveRoute.ts` 只放行报单/找机会/查持仓复盘
   三类），定投/情绪/心态话术被截走转讨论；分发接口层的直达能力
   （`intent.py`）实际到不了用户眼前。修法归属后续阶段（改预路由放行
   策略，或加快捷芯片），本轮零代码改动未处理。
2. **【验证边界】场景2/4 的讨论回答未验证**：只验证了「路由到讨论入口」
   的事实；讨论管线按禁真模型红线未跑，回答质量、接地域边界均未测。
3. **【测试环境说明】「未能完成：Failed to fetch」是测试防护造成的显示**，
   不是生产缺陷（生产上讨论管线会正常流式回答）；截图如实保留了这一态，
   复核时勿误判。
4. **【说明】mindset 缺种子的两个降级态在生产不可复现**（种子在场），
   均由 mock 注入验证；mock 与生产代码形状逐字段同构，且 `09` 的卡内态
   前端防御渲染与 `10` 的回落后端形状分别有组件级/单元级测试留证
   （card-render 线、mindset 线）。
5. **【既有局限记录】** `intent.py` 与 resolve 预路由均为无否定处理的
   子串/词表匹配（「别定投了」会命中定投），两线文档已自记该局限，
   本轮实测未新增反例。
