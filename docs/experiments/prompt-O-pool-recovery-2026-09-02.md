# Prompt O：深池环境盘点与重建（先盘点，后重建，忠实还原口径）

> 独立成文件，供分发给另一台机器上的 agent（无上下文，需要完整背景）。

你在 `biao-signal-system` 仓库工作（当前分支 `recovery/lei-round2`）。这是一个
规则型主观趋势交易信号研究系统（不做自动交易、不下单，只做技术信号研究）。

## 背景：为什么需要这个任务

2026-08-31 到 09-01 期间，系统跑过一批全池回测实验（exit-matrix、
stop-loss-matrix 等），依赖两份关键本机数据：

1. **`~/.lei_signal_lab/backtest_pool`**——175 个标的的完整历史 K 线数据
   （个股+ETF+指数混合池），是这批实验的原始输入。
2. **`~/.lei_signal_lab/backtest_runs/`**——工作台历史回测跑出的逐笔交易记录
   JSON（比如 8-31 矩阵实验的 1469/552/224 笔逐笔明细）。

09-01 发生过一次工作区回退事故，这两份数据当时靠 git stash 和一个还在跑的
本机服务进程内存兜底重建过一次。但到 09-02，多个后续任务（`exit-structural-stop-revival`、
`vt-signal-driven-sizing`、`time-stop-tail-aware` 三份归档，路径在
`docs/experiments/*-ARCHIVE-2026-09-0[12].md`，请先读这三份的"数据工程欠账"
一节）独立确认：**这两份数据现在在磁盘上完全消失了，stash 也不是 git 对象了**，
不是"重启即失"的临时状态，是已经丢了。

这些后续任务各自用了不同的替代样本（比如有的用 127 标的的临时重建池，有的用
641 笔的 ETF 子池），结果是：新报告的绝对数字和 8-31/9-1 那批老报告永久不可
横比，每个新任务都在用不同的、互相不兼容的小样本。

## 任务定位：先盘点，不要直接重建

**不要一上来就重新下载 175 个标的的 K 线数据去凑一个新池子。** 那样只会做出
第四个互不兼容的替代样本。本任务分两个阶段，第一阶段必须先完成并写出结论，
才能决定要不要进入第二阶段。

### 阶段一：盘点（必须做，产出决定后续是否继续）

1. **175 标的清单本身是否有权威留痕？** 搜索整个仓库（包括 git 历史，用
   `git log --all` 和 `git log -p` 查找），确认这 175 个标的具体是哪些代码/名称。
   优先查：
   - `docs/experiments/raw/` 下所有归档目录里是否有标的清单文件
   - 8-31 之前的 commit 历史里 `scripts/` 或 `configs/` 下是否有池子定义
   - 已有归档报告（`exit-matrix-report-2026-08-31.md`、
     `stop-loss-matrix-ARCHIVE-2026-09-01.md`）里提到的具体标的代码，把能提取到的
     标的名称列出来，交叉核对是否能拼出完整清单
   - **如果找不到权威清单，明确说"找不到"，不要自己猜一个凑数**。
2. **数据源和口径确认，不要猜**：读 `stop-loss-matrix-ARCHIVE-2026-09-01.md`
   和 `exit-structural-stop-revival-ARCHIVE-2026-09-01.md` 的"口径"一节，
   确认：数据源是东财还是腾讯（注意 `exit-structural-stop-revival` 报告已经
   发现两个数据源在部分高股息标的——000568.SZ、002326.SZ——上复权因子不一致，
   这是已知的数据源分歧点，重建时要留意）；时间窗口起点（1980年起还是别的）；
   前复权/不复权口径。
3. **历史 run 记录（逐笔 JSON）是否真的不可恢复？** 检查：
   - `git log --all -- "*.json"` 里有没有任何蛛丝马迹
   - 本机是否还有任何形式的备份（Time Machine、其他目录、云同步）
   - 如果确认全部不可恢复，明确写下"历史逐笔记录已永久丢失，8-31 矩阵的
     1469/552/224 笔逐笔明细不可复现，只能复现汇总统计数字（如果归档报告里
     留了汇总值的话）"。
4. **产出一份盘点报告**：`docs/experiments/pool-recovery-audit-2026-09-XX.md`，
   明确回答上面三个问题，附上找到的证据（文件路径、commit hash、报告引用行号）。
   如果三个问题里有任何一个的答案是"找不到/不可恢复"，在报告里明确说清楚
   这意味着重建出的池子会在哪些方面和老数据不同（比如标的数量不同、口径不同），
   不要含糊。

### 阶段二（仅当阶段一给出足够信息才做）：重建

只有当阶段一确认了标的清单、数据源、时间窗口这三项里**至少标的清单和数据源
两项**有明确依据时，才进入这一步。如果标的清单找不到，请停在阶段一，把盘点
报告交回，不要用你自己拼凑的清单去冒充"175标的池"——一个不完整或臆测的清单
如果被当成新基准使用，比继续用现有的多个小样本更有害（会制造虚假的一致性）。

如果条件满足：
1. 按盘点确认的口径重新抓取数据（复用 `src/lei_signal/data/` 下现有的
   provider 代码，不要重新发明抓取逻辑）。
2. **不要在重建过程中"顺手改进"标的清单**——比如发现某个标的数据质量差
   就换掉、或者觉得应该加几个更好的标的。忠实还原老口径优先。任何你认为
   应该改进的地方，写进报告的"建议"部分，不要在数据本体里改。
3. 重建完成后，**必须做锚定校验**：拿重建出的池子，对照现有归档报告里任何
   还留有具体数字的地方（比如某个标的某天的收盘价、某个回测的汇总 expR/PF），
   核对是否一致。如果对不上，说明口径还原有误，需要回头修正，不能直接使用。

## 硬性要求（不可跳过）

1. **重建结果必须入 git，不能再放在 `~/.lei_signal_lab/` 这类本机私有目录，
   也不能依赖任何进程内存**。这是本次事故的直接教训（`time-stop-tail-aware`
   归档的下一步方向第 3 条已经点名这个要求），如果重建完不落地，等于又白做
   一次，历史会第三次重演。
2. **只读探索阶段（阶段一）不改 `src/` 任何生产代码，不 push，不删除任何
   现有文件**。阶段二如果需要新增数据文件，只新增，不覆盖任何现有归档或
   raw 目录内容。
3. **两个阶段都不产生任何买卖点、不接入仓位系数、不修改任何现有 ARCHIVE 或
   SYNTHESIS 文档**——这是纯基础设施任务，不是策略研究任务。
4. 完成后不自行 push；产出留在本地分支，等用户统一核验后再决定是否合并。

## 输出

- 阶段一：`docs/experiments/pool-recovery-audit-2026-09-XX.md`
- 阶段二（如果执行）：重建的数据文件放在 `docs/experiments/raw/pool-rebuild/`，
  附一份 README 说明口径来源、锚定校验结果、与老数据的已知差异清单。

如果阶段一发现标的清单/数据源/时间窗口都找不到权威依据，直接停在阶段一，
在报告结论里写清楚"建议不重建，理由是缺乏可信依据还原老口径，重建出的池子
会制造新的、看似权威但实际是臆测的基准"——这是一个合法且可能是正确的结论，
不要为了完成任务而在缺乏依据的情况下强行进入阶段二。
