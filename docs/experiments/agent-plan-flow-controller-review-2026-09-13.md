## 3. 固定补修C1：持仓监督遗漏版本拦截

文件：`web/src/components/CreatePlanDialog.tsx`。

`canSubmit` 和 `submit()` 检查了版本，但持仓监督使用的是另一套 `canSubmitHolding` / `submitHolding()`，其中没有对应检查；`createHolding` 仍传 `rulesetVersion ?? ""`。版本读取提示也只渲染在技术入场分支。

独立输入：持仓监督退出预案、有效期和触发条件都齐全，`rulesetVersion=null`。实际结果：

```json
{"canSubmitHolding": true, "request.ruleset_version": ""}
```

这直接违反P1两条创建路径“读不到不提交”。本次只证明产生空版本请求，不将它夸大为已证明真实计划会错误生效。代码里“空版本确认必409”的注释也不准确：既有确认检查为 `if plan.ruleset_version and ...`，不能把它当客户端失败兜底。

**最小修复**：对技术入场、持仓监督、讨论新建的版本就绪判断与失败提示保持一致；按钮与提交函数均检查有效版本，持仓页也能重新读取。不要用新硬编码常量替代，也不要为修页面改确认规则。编辑既有草稿仍保留其版本与引用，不把普通编辑变成重标版本。

**固定验收**：技术/持仓/讨论各测读取中、失败、恢复成功。其余必填字段均填齐再测试版本失败，避免“其实被其他空字段禁用”误判。失败时无创建请求、恢复后用权威版本；持仓原有字段要求保持。

## 4. 固定补修C2：稳定编号不等于冻结了首次保存请求

文件：`web/src/components/PlanDraftCard.tsx`；配合现有 `api/routes/plans.py::_draft_request_hash`，服务端校验不应被放松。

当前 `clientRequestId` 不含版本，但每次保存重新 `buildPayload(rulesetVersion)`；同一编号的业务摘要在服务端仍包含版本。网络响应丢失或失败后，查询缓存更新版本，再点保存，就会给旧编号配新内容。

主控抽取真实前端保存函数，模拟首次请求已经提交但响应丢失，随后版本从2.1.0变3.0.0：两次请求编号相同、版本不同。真实后端临时库对照为：

| 请求 | 结果 |
|---|---|
| 首次2.1.0 | 201，保存一张草稿 |
| 完全相同请求重试 | 201，原plan_id |
| 同编号改成3.0.0 | 409 `DRAFT_REQUEST_CONFLICT` |

原草稿未丢失，但用户不能通过这次重试取回它；前端“未落库，可重试”的失败文案也不能覆盖响应丢失的情况。

**最小修复**：首次发起时固定完整保存请求（包括采用版本），不确定结果后的重试复用原请求和身份；已有绑定优先读回原plan_id。用户真正修改内容属于新业务，不能伪装成重试。保留服务端“同编号不同内容409”的保护，不把版本从业务摘要删掉来隐藏问题。

**固定验收**：真实后端已保存，但客户端第一次未收到成功响应；版本更新后重试，仍取回同一plan_id、原版本和原冻结引用、计划数不增。原请求尚未成功的失败也可用同一快照重试。跨会话响应不串入新卡片。错误文案说“暂不能确认是否保存成功，正在/可重试核对”，不能断言未落库。

## 5. 固定补修C3：版本冲突不能继续指示原地编辑即可解决

文件：`web/src/components/ReviewDrawer.tsx`，同时检查 `PlanDraftCard` 的错误解释。

`ReviewDrawer` 对所有错误无差别追加“可直接点编辑计划补齐后重试，无需新建计划”。主控调用真实错误回调得到：

> 版本已变，请复核后重建草稿（可直接点「编辑计划」补齐后重试，无需新建计划）

普通编辑不改版本，这是保护旧依据的正确设计；因此该指示会让用户反复进入无法消除409的循环。

**最小修复**：按已有错误代码区分处理。缺字段/符合性问题引导编辑原草稿；分析不可用引导稍后重试；`RULESET_VERSION_CHANGED` 清楚说需要按当前依据重新核对并另建草稿，旧计划保留，使用已有讨论/新建入口。不能自动改版本、删除旧计划或替用户确认。

**固定验收**：同一页面分别展示422字段/符合性、503分析不可用、409版本变更，提示不冲突；旧版本计划编辑后仍保留旧版本，不能通过“修文案”改变确认纪律。无需开发通用旧计划迁移器。
