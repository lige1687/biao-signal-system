# Agent 运行时采用包：异常恢复保护返修

日期：2026-09-17

## 一句话结论（大白话）

部署中途失败后，恢复脚本现在会先确认所有文件仍是这次部署留下的样子、所有备份也完好，再开始恢复；只要有人后来改过文件或备份损坏，它会整批拒绝且一个文件也不碰，恢复写入本身失败也会明确报错并保留材料。

## 范围与策略关系

本次只修复隔离采用包的部署可靠性，服务于系统运行工具层。没有修改交易规则、阈值、技术判定、产品源码或真实数据库；道路、路牌、入场触发和过滤纪律均保持不变。

## 根因

正常 `apply.sh` 和 `revert.sh` 已经会在写入前检查目标状态，但中途失败生成的 `restore-partial.sh` 直接执行 `cp` 或 `rm`。这条异常出口没有再次检查目标文件和备份，因此会覆盖失败后产生的新编辑；直接复制也可能先截断目标文件再报错。

## 修复

- 保留 `restore-partial.sh` 调用入口，由它调用随恢复材料保存的 `recovery.py`。
- 每次成功改动后，把该文件的“当前应有状态、恢复后状态、恢复载荷”写入恢复计划。
- 恢复开始前一次性检查所有目标状态和所有恢复载荷的 SHA-256；任何一项变化或损坏都整批拒绝，目标零写入。
- 恢复复制先写同目录临时文件，核对内容后再原子替换；写入失败返回非零，打印已恢复数量，并保留恢复材料供诊断和人工核对。
- `revert.sh` 恢复基线时也改为临时文件加原子替换，避免失败当前项被直接复制截断后又没有进入恢复清单。

## 验证

针对性探针覆盖六种情况并返回 0：apply 失败后完整恢复、apply 失败后有人修改则整批拒绝、备份损坏则整批拒绝、恢复写失败返回非零、revert 失败后有人修改则整批拒绝、revert 失败后完整恢复。

旧探针也返回 0：正常 24 项应用和精确回退保持；缺目标、包内容损坏、依赖变化、目标变化和正常回退时的后续编辑保护均保持。旧探针原来会覆盖后续编辑的异常场景现在返回非零，并保留该编辑。

证据：

- `docs/experiments/raw/agent-adoption-recovery-protection-2026-09-17/recovery_probe.py`
- `docs/experiments/raw/agent-adoption-recovery-protection-2026-09-17/recovery-probe-results.json`
- `docs/experiments/raw/agent-adoption-recovery-protection-2026-09-17/verification.txt`

目录卫生检查只报告隔离 git worktree 根目录自带的 `.git` 控制文件；本次新增文件没有被报告为放错位置。

## 限制

恢复不是跨 24 个文件的单一原子事务。开始恢复前能保证变化或备份损坏时零写入；如果恢复过程中出现新的磁盘或权限故障，已经成功恢复的项会保留，命令返回非零并报告完成数量。此时原恢复计划不支持直接重跑，因为已完成项的状态已经改变；必须按输出数量和保留材料人工核对已恢复项与剩余项，再决定后续操作。
