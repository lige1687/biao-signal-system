# 系统待升级项目：目标与进展的长期记录

2026-09-08 用户要求建立。界面入口：`/upgrades`，主导航「策略研究 → 系统待升级」。

OKR 在这里指“想达到的目标，以及判断有没有做到的具体结果”。分两类：

- **方向性目标**：长期希望改善什么；可以有多个具体目标，不用猜测完成百分比。
- **具体目标**：一次能推进、能验收的工作，写清所属方向、完成标准、依据和下一步。

每次用户提出系统研究或升级目标，先检索已有条目：相同目标补充原条目，新的目标登记新条目；不能只留在聊天里。只登记本次会话已经讨论的目标，不假称所有历史任务已经迁入。

新目标默认待规划或待授权。用户授权后，记录原话或明确范围，再标为已授权；授权一个具体目标，不代表同方向下所有工作都获准执行。已授权只表示可推进，不会自动创建任务、运行回测或修改交易规则。未来通过聊天推进时，agent 先读本台账，核对授权范围再行动。

每次推进记录实际工作、证据和下一步；完成标准逐项勾选。材料齐备后提交待验收，由用户验收后标完成。研究证伪也可以完成，但必须写清结论；不能把“研究做完”误写成“策略有效”。搁置或不采纳保留历史，不能删除失败记录。

论文方向：以执行当时近三年的研究为主，优先最近十二个月，经典限与系统高度相关者；查看原文、发表/修订时间、支持及反向证据。候选可以超出 A/B/C/D。若无法追溯现有规格，应登记为体系扩展提案，待用户决定如何补充规格；不得伪装成现有原始规则。基本面和消息面只解释背景的边界继续有效。

## 实现与交接

运行数据存于服务端独立 SQLite 文件，默认在应用数据库同目录的 `system_upgrades.db`，可用 `LEI_UPGRADES_DB` 指定。页面可导出完整 JSON（含进展、来源与授权历史）。`initial.json` 是首次安装的初始条目，初始化只执行一次，不覆盖后续修改。每次写入有版本冲突检查和追加历史。

接口：`GET /api/upgrades`、`POST /api/upgrades`、`PATCH /api/upgrades/{id}`、`POST /api/upgrades/{id}/actions`、`GET /api/upgrades/export`。先读取当前版本再修改；不能通过普通编辑伪造授权或完成。接口是现有本地单用户应用的一部分，授权记录表示用户工作意图，不是多用户身份认证或自动执行许可系统。

API 目标编号长期稳定；页面 `?goal=编号` 可定位。进展数据在服务端保存，刷新、换浏览器不丢失。备份运行数据库或导出 JSON；初始种子不包含后续进展。
